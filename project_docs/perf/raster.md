# Растр глобуса (заливка по кускам GVE2): где такты и как ускорить

2026-10-24. Сборка `tmp/build/oxz.spg` от 02:18, её копия — `tmp/perf/raster/base/`. Только замеры и
прототипы в `tmp/perf/raster/`, исходники не тронуты.

**Как мерили.** Свой ini и свои метки: `gen_labels.js` ставит метку на **каждую инструкцию**
`globe_s.s` / `globe_sh_s.s` (из `.lst`), поэтому профиль даёт число исполнений и такты каждой команды
(`analyze.js`, `summary.js`). Сценарии — `runx.js` (новая игра → геоскейп → зум → `poke 06:0038 час` →
профиль одного поворота `key RIGHT`); время игры заморожено (`poke 32:88DD 0` — `step_sec[0]`), чтобы
прогоны были сравнимы. **T14** — такты 14 МГц (такты профиля x 4), **кадр = 286 720 T14**.
Прототипы `eh.s` и `ec.s` собраны sdasz80 в свободный хвост банка 24 (#B520..#B94B) и вписаны через
`poke` с перенацеливанием `call` в `render` (globe.s:1514 и :1563). Картинку проверяли не снимком, а
дампом заднего буфера (строки 280..479, оба полукадра — `cmpdump.js`): **0 отличающихся байт** в
36 видах (зумы 0–5, поворот и наклон) при 18:00 и ещё в 36 при 12:00, у `ec` — в 6 сменах солнца.

**Почему столько.** На зуме 0 диск виден целиком: в строке в среднем 9.6 активных кусков, и
каждый визит почти всегда даёт отрезок DMA (1755 из 1919; граница всегда меняет текстуру —
конвертер оставил только такие рёбра). Куски короткие — в среднем **4.2 строки** (1919 / 452):
мелкая береговая линия часто меняет наклон. Поэтому на визит приходится ещё ~225 T на начала,
концы и разбор кусков — итого **~720 T на отрезок** против ~270 T у готового списка отрезков. На
зумах 2–5 куски длинные (15–35 строк), и там растр — это визиты, отрезки и строки (~860–1060 T на
строку x 200 — половина растра зума 5).

Прочее: память Win3 (страница рёбер) не кэшируется — +1…3 T на обращение, ~8 % `eg_walk/eg_step`.
Ожидание DMA в растре — 3 % на зуме 0 и **24 % на зуме 5** (длинные отрезки BLT2): там упор
частично в DMA. По классам команд (зум 0): загрузки из памяти 26 %, `ld r,r/n` 20 %, переходы 9 %,
OUT 7 %, call/ret 5 %.

**Смена солнца на том же виде** (время идёт — `scr_geo.c:979`, не чаще раза в 25 кадров) идёт тем же
полным проходом кусков: на зуме 0 — 8 кадров рендера, растр те же 5.43 (замер `out/sungrid0.txt`).

### Б. Алгоритмические

**Б1. Кэш отрезков вида (тот же вид — другое солнце, возврат к виду).** Пока идёт проход кусков,
писать «число, (слов − 1, текстура)…» на строку (как уже делает `cap_row`, globe_s.s:3573, для
рёберного пути; запись ~58 T на отрезок), при смене солнца на том же виде — повторять список
циклом `ec` (ниже). Отрезки от солнца не зависят: тень выбирается флагом строки EP_SHF при выводе.
Замер цены повтора на зуме 0 (`ec.s`, 1983 отрезка): **1.78 кадра растра против 5.43** (база) / 4.39
(А) → смена солнца на зуме 0: рендер 8 → ~4.5 кадра; по числу отрезков: зум 1 ~2.0 (против 5.86),
зум 2 ~1.3 (3.20), зумы 3–4 ~0.85 (1.9), зум 5 ~0.7 (1.5). На быстром времени эпоха солнца
меняется каждый такт, перерисовка — раз в 25 кадров (`scr_geo.c:979`): сейчас глобус зума 0 съедает
~8–9 кадров из 25 (~35 %), с кэшем — ~4.5 (~18 %). Писать лучше не при повороте, а в первой смене солнца на виде
(повороты не платят +0.39 кадра записи). Память: одна страница пула 16 КБ (вид зума 0 ~4.1 КБ —
влезает 3 вида, можно держать последние и для поворота туда-обратно); в странице рёбер места нет
(после EP_VIDX свободно ~2.4 КБ). Риск для картинки — нет. Сложность — средняя.

**Б2. Вывод списка отрезков со встроенным выводом в порты (`ec.s`, замерено).** Тот же приём А5
для `rp_row` (globe_s.s:2985–3056 — пути `_gl_rows_cap` и `_gl_rows_pre`): 271 → ~204 T14 на отрезок,
зум 0: **2.24 → 1.78 кадра** (−0.46, −21 %), дампы 6 смен солнца побайтно те же. Здесь уже 8 %
времени — ожидание DMA: дальше упор в BLT2, а не в процессор. +~240 байт в банке 24.

**Б3. Зумы 0–1 — виды списками отрезков на карте вместо кусков (смена формата).** На зумах 0–1
куски короткие, разбор GVE2 стоит ~450 T на отрезок сверх вывода — поэтому GVE2 там медленнее
GVW1 (globe.md §12.11: 8 / 10 кадров против 5 / 7). Если для z0 (и z1) класть в GVIEW.PAK поток
отрезков, движок уже есть (`_gl_rows_pre`, globe_s.s:2962, + Б2): поворот на зуме 0 — растр
**5.43 → ~1.8 кадра** (рендер 9 → ~5.5), на зуме 1 — 5.86 → ~2.0 (10 → ~6). Размер: z0 168 видов x
~4.1 КБ = 0.68 МБ вместо 0.45 МБ GVE2, z1 1104 x ~4.8 КБ ≈ 5.3 МБ вместо 2.6 — пакет 14.1 → ~17 МБ.
Чтение с карты +2–4 сектора (+0.1–0.25 кадра при нынешнем `_sd_rd`). Риски: вид ≤ #1C00 байт
(EP_VIEW..EP_VIDX) — у полярных видов z1 может не влезть, нужен флаг формата на вид с откатом на
GVE2; конвертер (`Core/GlobeViews.cs` уже даёт пары пути А) + флаг формата в `globe_view.s`.
Картинка та же (поток — те же пары, что сверяются с путём А). **Решение по объёму — за пользователем.**

**Б4. Перекрыть DMA тени работой растра** (конвейер по строкам блоков: подкладка 4 строк → их
отрезки). Ожидание DMA тени на зуме 0 в 18:00 — 0.15 кадра (`iv_out`), растра — 0.01–0.1: выигрыш
≤ 0.2–0.3 кадра, сложно. Позже.

**Отклонено (не окупается или меняет вид):** 2D DMA на несколько строк (строки узора одной текстуры
лежат через 14x256 байт, шаг 2D — 256/512); склейка отрезков (каждая граница меняет текстуру);
океан без подкладки O через BLT2 (формулы разные: `getLandShadow` — shadow/3, `getOceanShadow` —
shadow, REF/OpenXcom/src/Geoscape/Globe.cpp:203–217); таблицы ячеек в кэшируемую память (кэш 512 байт
прямого отображения общий с кодом, нужны 2 КБ выровненных страниц, выигрыш ≤ 5–8 %); раскрутка
`djnz` (−2 T).

## 3. Что делать первым

1. **А1–А5** (`eh.s`) — готовый проверенный код, −1.0…−1.2 кадра на зумах 0–1, −0.75 на 2, −0.2…−0.36
   на 3–5, +163 байта. Риска нет.
2. **Б2** (`ec.s`) — −0.46 кадра на повторе отрезков; нужен для Б1 и Б3.
3. **Б1** (кэш отрезков вида) — −3.6 кадра на каждой смене солнца на зуме 0 (−1…−3.9 на других):
   главное для геоскейпа с бегущим временем. Одна страница пула.
4. **Б3** (z0–z1 списками отрезков) — −3.6/−3.9 кадра на поворот z0/z1, но +3 МБ данных и правка
   конвертера: только с согласия пользователя.
5. **А6** — остатки (строка, начала/концы) — −0.2…−0.5 кадра.
