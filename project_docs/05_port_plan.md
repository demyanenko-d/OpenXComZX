# Архитектура порта и поэтапный план

Документ сводит 02 (железо), 03 (сборка), 04 (OpenXcom), 06 (данные) в
решения. Статус каждого решения: **[принято]**, **[гипотеза]** — требует
прототипа и замеров, **[открыто]** — нужен выбор.

## 1. Общая архитектура

### 1.1 Формат программы — [принято]

- Один автономный **SPG 1.0** (см. 03 §6): весь код игры + ядро.
  Запуск из Wild Commander, после старта WC больше не нужен.
- Ассеты — отдельные файлы на SD (FAT32), читаются своим драйвером
  (порт `REF/frontend/z80_fw`, см. 03 §7).
- Оригинал был разделён на `GEOSCAPE.EXE` / `TACTICAL.EXE` (см. 06). У нас
  кода ~200–400 КБ — **весь код держим в памяти одновременно**, а при смене
  режима (геоскейп ↔ бой) перезагружаем только ассеты. Состояние кампании
  живёт в своих страницах, передача через файл не нужна (файл — только для
  сохранений).

### 1.2 Тулчейн — [принято]

- SDCC 4.5 (`--sdcccall 1`), sdasz80; горячие места — ассемблер.
- Код в нескольких страницах: SDCC `__banked` + свои `set_bank`/`get_bank`
  (запись #12AF), один `--codeseg` на банк.
- Node.js: упаковщик `mkspg.js`, генераторы таблиц, **офлайн-конвертер
  данных** из `Steam/…/XCOM`.
- Проверка перекрытия секций по `.map` в каждой сборке (sdld молча
  накладывает секции).
- Без плавающей точки на Z80: фиксированная точка, таблицы.

### 1.3 Карта окон CPU — **заменено: см. 08 §4** (Win1 — страница данных, Win2 — банки кода)

Ниже — первоначальный вариант (история).

| Окно | Назначение | Кэш |
|---|---|---|
| Win0 #0000 | страница-«ядро» в ОЗУ (MemConfig = W0_RAM\|W0_MAP_N\|W0_WE): таблица IM2 и ISR, трамплины банков, драйвер SD/FAT, DMA-хелперы, буферы секторов, стек | да |
| Win1 #4000 | общий C-код, глобальные переменные, runtime SDCC | да |
| Win2 #8000 | банкованный код (`__banked`) | да |
| Win3 #C000 | окно данных (карта боя, правила, ассеты) | **нет** — сюда пишет DMA |

Правило когерентности (02 §2): **DMA не пишет в страницы, стоящие в
кэшируемых окнах.** Win3 некэшируемое; видео- и графические страницы CPU
почти не читает.

### 1.3a «BIOS игры» в странице ядра — [принято, идея пользователя]

Страница ядра (Win0, стр. #04) — сервисный слой игры, общий для всех
модулей и не зависящий от банкинга Win2:
- прерывания (кадровое, DMA, строчное), таблица IM2;
- **очередь команд DMA** (§2.5);
- ввод: драйвер мыши/клавиатуры с абсолютным курсором;
- далее: SD/FAT, управление страницами и банками, музыка OPL3, отладочный вывод.

Вход в сервисы — через **таблицу переходов по фиксированным адресам**
(стабильный ABI для C и asm). Эмулятор знает адреса по меткам и может
перехватывать сервисы и подменять ответы/состояние в тестах (сейчас —
`poke`/`expect` по меткам, 07 §5). Фактическая раскладка страницы ядра:
`#0000` RST, `#0200-#1FFF` код (`_KERNEL`), `#2000-` данные (`_KDATA`,
кольцо DMA 4 КБ), стек вниз от `#3E00`, векторы IM2 `#3EFB-#3F00`.

### 1.4 Бюджет памяти — [гипотеза]

Доступно #00–#EF = 240 страниц (02 §3).

| Назначение | Страниц | Объём |
|---|---:|---|
| Экран 256c: два буфера + неподвижная панель (выравнивание 16 стр.) | 16 | 256 КБ |
| Ядро (Win0) + общий код (Win1) | 2 | 32 КБ |
| Банкованный код | 16–24 | 256–384 КБ |
| Правила, строки, шрифты | 4–8 | 64–128 КБ |
| Состояние кампании | 2–4 | 32–64 КБ |
| Карта боя (10 000 тайлов x 8–12 байт) | 8 | 128 КБ |
| Поиск пути, FOV, рабочие массивы | 4 | 64 КБ |
| Графика местности миссии (листы с шагом 512, обрезанные кадры) | 24–40 | 384–640 КБ |
| Юниты миссии в RLE (как PCK) | 12–16 | 192–256 КБ |

## 2. Видео

### 2.1 Режим — [принято]

**320x240, 256 цветов** (RRES = 10, VM = 10). Причины:
- графика оригинала — 8 бит, палитра боя — 16 рамп x 16 оттенков;
- 16c даёт одну 16-цветную палитру на весь битмап — не подходит;
- DMA BLT1 с побайтной прозрачностью (ASZ = 1) — родной для 256c;
- 4 МБ позволяют держать графику одной миссии в 8 битах (06).

Палитры: 6-бит VGA → CRAM, `v24 = round(v6·24/63)` (ШИМ-ЦАП различает
0–24, 02 §4). Смена палитры — DMA RAM→CRAM за доли кадра.

### 2.2 Буферизация и сплит — [гипотеза]

- Холст 256c = 512x512; две половины по 256 строк → двойной буфер
  переключением GYOffs (0 ↔ 256).
- Боевая панель (320x56 внизу) рисуется **один раз** в неиспользуемых
  строках холста; кадровый INT на строке 184 перезагружает GYOffs на адрес
  панели (02 §4 «перезагрузка GYOffs»). Панель не перерисовывается при
  скролле карты.
- Ширина холста 512 при экране 320 → **96 пикселей запаса с каждой стороны
  для аппаратного скролла по X** без перерисовки.

### 2.3 Рендер изометрии — [гипотеза, главный риск проекта]

Основа — «перерисовка вида из спрайтов через DMA», а не полный
программный рендер:

1. Вся графика лежит в **листах с шагом строки 512 байт** (как экран). Тогда
   блит любого подпрямоугольника = один DMA BLT1 с S_ALGN|D_ALGN|ASZ:
   DMALen = w/2 − 1, DMANum = h − 1. Отсечение по «грязному» прямоугольнику
   — тривиально.
2. Кадры обрезаются офлайн по габаритам непрозрачных пикселей (пол 32x16,
   стены узкие) — в среднем ~50% от 32x40.
3. Порядок художника как в OpenXcom (04 §3): z → x → y, внутри тайла пол,
   стены, объект, предметы, юниты.
4. **Полная перерисовка вида** (скролл, смена уровня): ~800 блитов,
   ~480 КБ через BLT1 при ~74 КБ/кадр → **~7–8 кадров (~0.15 с)** плюс
   настройка DMA (~300 тактов на блит). Для пошаговой игры приемлемо;
   оригинал тоже скроллит рывками.
5. **Инкрементальная перерисовка** (анимация, ход юнита, дверь): только
   «грязный» прямоугольник — перерисовать все части тайлов, пересекающие
   его, в порядке художника с отсечением.
6. **Затенение:** DMA не умеет затенять с прозрачностью в 256c
   (BLT2 прибавит тень и к прозрачным пикселям, см. 04 §10). Поэтому —
   **кэш заранее затенённых спрайтов**: ключ (кадр, уровень тени);
   промах — CPU проходит по кадру таблицей `(p & #F0) | min((p & 15) + s, 15)`
   (~25–40 тактов/пиксель, ~1–2 мс на обрезанный кадр); LRU в пуле страниц.
   Днём почти всё с тенью 0 — кэш почти не нужен; ночью — несколько уровней.
   Неразведанное — чёрное (заливка, не блит).
7. **Юниты:** кадр собирается из частей (ноги, торс, руки, оружие — 04 §3)
   через BLT1 в кэш собранных кадров, затем затеняется и блитится как
   обычный спрайт в порядке художника.
8. **Аппаратные спрайты TSU** — только для того, что поверх всего: указатель
   мыши, возможно, трассеры/всплывающие иконки. Их цвета берутся из
   16-цветного блока CRAM (например, серая рампа 240–255 палитры боя).
   Для юнитов TSU не годится — нет перекрытия стенами.

**Точка «идти/не идти» — этап 3:** прототип рендера на реальной карте с
замером кадров на полную и инкрементальную перерисовку, днём и ночью.

Запасной вариант, если не хватит скорости: предрендер статической карты
текущего уровня в большой буфер (50x50 ≈ 1600x912 ≈ 1.46 МБ) и копирование
видимой части DMA каждый кадр (~59 КБ, <1 кадра). Дорого по памяти — тогда
юниты хранятся только в RLE.

### 2.5 Очередь DMA («display list») — [принято, идея пользователя, прототип работает]

Производитель кладёт 9-байтные команды (адреса источника/приёмника,
длина, число пачек, DMACtrl) в кольцо на 255 записей в странице ядра; по
окончании передачи DMA выставляет INT (вектор #FB), `isr_dma` запускает
следующую команду девятью `OUTI` (`src/kernel/dmaq.s`, `src/inc/dmaq.h`).
CPU в это время считает логику.

Замер (эмулятор, 250 блитов BLT1 32x40 = 320 КБ): с опросом статуса — 5
кадров, CPU занят; через очередь — 4–5 кадров, после постановки CPU
свободен ~1.7 кадра. Блиттер ~80 КБ/кадр.

Развитие: команды-маркеры (сигнал «кадр готов», смена регистра видео,
например GYOffs для переключения буфера — как copper list), «вызов»
заранее собранных списков (перерисовка панели), пропуск неизменных
регистров (адреса продолжаются после передачи). Правило: при работающей
очереди регистры DMA напрямую не трогать — все передачи, включая
CRAM/SFILE/SPI, только через неё.

### 2.4 Интерфейс и текст — [гипотеза]

- Шрифты OpenXcom (`bin/common/Language/*.png`, с кириллицей) → 1-бит глифы
  + ширины; вывод текста — CPU по маске или DMA BLT1 из листа глифов,
  заранее окрашенных под цвет рампы.
- Виджеты (окно, кнопка, список, полоса) — один маленький набор на всю игру
  (оригинальные ~34 файла виджетов сводятся к нескольким сотням строк C).
- Экраны 320x200 центрируются в 320x240 (сдвиг на 20 строк, 04 §8).

## 3. Тактический бой — алгоритмы под Z80

| Подсистема | В OpenXcom | На Z80 — [гипотеза] |
|---|---|---|
| Хранение карты | ~250 байт/тайл | 8–12 байт/тайл: id 4 частей, флаги, свет, дым/огонь, видимость, индекс юнита; предметы — отдельный список |
| Проходимость | `getTUCost` на лету | предрасчёт байта стоимости/стен на тайл при загрузке и при разрушениях |
| Поиск пути | A* по всей карте, узел 48 байт | A* / Дейкстра в ограниченном окне, узел 3–4 байта, куча в странице |
| Поле зрения | FOV всех юнитов после каждого шага | shadowcasting по уровням на тайлах; пересчёт только для идущего юнита + обратная проверка «кто видит его» |
| Линия огня | до ~37 воксельных лучей | 1–3 луча; LOFTEMPS оставляем (3.6 КБ) |
| Выстрел | воксельная трасса до 16 000 вокселей | Брезенхем в вокселях с обрывом на краю карты; шаг крупнее по пустым тайлам |
| Взрывы | 4477 лучей, double | 3D-заливка (flood fill) с затуханием по тайлам |
| Освещение | 3 слоя, sqrt | окружающий свет + несколько источников, таблица расстояний |
| ИИ | много `findReachable` + `canTargetUnit` | патруль по RMP, ближайшая видимая цель, ограниченный перебор укрытий; ход пришельцев в несколько секунд допустим |
| Генерация карты | MapScript | как есть (целочисленная, дешёвая) |
| RNG | xorshift64* | 32-бит xorshift |

2. **Предрендеренные кадры глобуса** (офлайн) — ближе к оригиналу, но
   сотни кадров, объём и загрузка с SD под вопросом.
3. Программный глобус на таблицах — самый дорогой, вряд ли.

Рекомендация: начать с варианта 1, вариант 2 рассмотреть позже.

планировщик (ближайшее событие: прибытие корабля, конец исследования, спавн

## 5. Звук и музыка

### 5.1 OPL3 — [принято как опция]

- Плата MoonSound-совместимая: #C4/#C5 (банк 0), #C6/#C7 (банк 1), в Unreal
  `MoonSound=1` (02 §7).
- **Определение наличия** — стандартный тест таймеров OPL (флаги статуса)
  при старте; нет платы → без музыки (или см. 5.3).
- **Плеер ADLIB.CAT** — порт `src/Engine/Adlib/adlplayer.cpp` на Z80
  (целочисленный, небольшой; 04 §6). 12 голосов: 0–8 → банк 0, 9–11 → банк 1.
  Стерео-хорус оригинала — опционально (9+9 каналов с панорамой, тогда
  голосов меньше).
- Тик ~70 Гц; при кадре ~48.8 Гц нужен таймер: несколько кадровых INT за
  кадр (механизм из `REF/src_sdcc/asm/isr.s`) или аккумулятор темпа.
- При NEW = 1 выставлять биты L/R в C0–C8 (иначе тишина).
- **Проверить на железе** запись в OPL на 14 МГц и алиасинг портов с
  #7FFD/#FE (02 §11 п.3) — использовать B ≥ #80 в старшем байте адреса.

### 5.2 Звуковые эффекты — [открыто]

Сэмплы (`SOUND1/2.CAT` 6 бит 8 кГц, `SAMPLE*.CAT` 8 бит 11 кГц) — вывод
через Covox/SounDrive требует ISR на частоте дискретизации (дорого) и
наличия ЦАП (на реальном TS-Config не подтверждено). Варианты: короткие
FM-эффекты на OPL3; редкие сэмплы через GS/NeoGS, если есть; без эффектов.

### 5.3 Без OPL3 — [открыто]

Конвертация ADLIB.CAT в AY/TurboSound офлайн — возможно позже, низкий приоритет.

## 5a. Рамки (решение пользователя)

Без модов и плагинов, без гибкой настройки: одна зафиксированная
конфигурация (ванильный `xcom1`, опции по умолчанию), правила
«запекаются» конвертером. Один язык интерфейса, если несколько — дорого.
Это убирает из порта: загрузку/слияние правил, экраны опций и модов,
Unicode/плюрализацию, большую часть `Menu/` и `Mod/`.

## 6. Конвейер данных (конвертер на Node.js)

Вход — копия пользователя (`Steam/XCom UFO Defense/XCOM`) + правила
OpenXcom (`REF/OpenXcom/bin/standard/xcom1/*.rul`, язык, шрифты).
Выход — каталог файлов для SD. **Данные не распространяются**, пользователь
запускает конвертер сам.

| Вход | Выход |
|---|---|
| `PALETTES.DAT`, `BACKPALS.DAT` | палитры CRAM (15 бит, уровни 0–24) |
| `TERRAIN/*.PCK/TAB` | обрезанные кадры в листах с шагом 512 + таблица (x, y, w, h, смещение) |
| `TERRAIN/*.MCD` + `mcdPatches.rul` | урезанные записи MCD |
| `UNITS/*.PCK/TAB` | RLE-кадры (формат, удобный для Z80) |
| `UFOGRAPH/*`, `GEOGRAPH/*` (SCR/SPK/PCK/DAT) | экраны и иконки, дополненные до 320x240 |
| `MAPS/*.MAP`, `ROUTES/*.RMP` | как есть |
| `LOFTEMPS.DAT` | как есть |
| `WORLD.DAT` + `TEXTURE.DAT` | плоская карта мира 512x256 (вариант 1) |
| `*.rul` (YAML) | бинарные таблицы (предметы, юниты, броня, исследования, производство, постройки, миссии, …) |
| `en-US.yml` / `ru.yml` | упакованные однобайтовые строки (CP866 или своя кодировка) |
| шрифты PNG | 1-бит глифы + ширины |
| `SOUND/ADLIB.CAT`, `AINTRO.CAT` | как есть (или предразбор) |
| `.nam` имён солдат | упакованные таблицы |

Зависимость: YAML-парсер для Node (`js-yaml` через npm — npm работает).
Для чтения PNG — маленький декодер (или `pngjs`).

Эталон правильности — загрузчики OpenXcom (04 §7). Для сверки полезно
собрать OpenXcom на ПК (CMake + VS 2026 есть) и сравнивать картинки.

| TSU-спрайт курсора, мышь, клавиатура | работают |

Осталось: банкинг кода (`__banked`), образ SD со своими файлами.

Исходный план этапа:
- Структура каталогов проекта (`src/`, `tools/`, `build/`, `data/`), git.
- Исправленный `tsconf.h` (02 §12), `types.h` (конвенция sdcccall).
- Скрипты сборки: SDCC → ihx/bin по страницам → `mkspg.js` → SPG; проверка
  `.map`.
- Эмулятор: `unreal/build/debug/Unreal.exe` (SDL + ImGui, ведёт
  пользователь). Нам: свой ini (`SDCARD=` на наш образ, `[AUTOLOAD]
  snapshot=` на SPG), образ SD через `unreal/tools/robimg/robimg.exe`,
  генератор меток `bb:xxxx имя` из `.map` SDCC, скрипт «собрать и
  запустить»; затем отладочные средства под проект (см. 01).
- «Hello world» SPG: ядро в Win0, IM2, 320x240 256c, палитра через DMA,
  DMA FILL, кадровый INT, клавиатура и мышь, `__banked` вызов.
- **Замеры:** реальная скорость C-кода на 14 МГц с кэшем и без; DMA BLT1

## 8. Риски

| Риск | Влияние | Что делаем |
|---|---|---|
| Скорость рендера изометрии | критично | прототип на этапе 3, запасной вариант с предрендером |
| Скорость ИИ/FOV/пути | высокое | алгоритмы из §3, ассемблер в горячих местах, замеры |
| Объём кода SDCC (~5–10 байт на строку C) | среднее | банкинг, урезание экранов, `--opt-code-size` |
| Кэш CPU vs DMA | среднее | правило §1.3, тесты на железе |
| Расхождения эмулятора и железа | среднее | ранние тесты на реальном TS-Config (OPL-порты, SD, мышь) |
| Нет спецификаций SPG, OPL-таймингов, скорости SPI | низкое | восстановлено по коду (03, 02), проверять |
| Юридическое: данные оригинала | — | только конвертер, данные не распространяются |
