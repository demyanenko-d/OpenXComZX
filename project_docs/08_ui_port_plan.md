## 1. Вывод: делаем

Интерфейс OpenXcom — это экраны-состояния на небольшом наборе виджетов и
целочисленная логика над моделью игры. На Z80 это реально: экраны
пошаговые, перерисовка по событию, не каждый кадр. Ограничения —
объём кода (~150–250 КБ после порта → банкинг), текст (много строк
→ быстрый вывод глифов) и отсутствие YAML/строк на Z80 (→ всё
«запекает» конвертер).

## 3. Как портируем C++ → C

- **Экран = структура с «методами»**: `init`, `handle(event)`, `think`,
  `draw`, `free`; стек экранов (как `Game::pushState/popState`), глубина ≤8.
  Ввод и `think` — только верхний экран, как в OpenXcom.
- **Виджеты** — статические массивы в данных экрана; общий заголовок
  (тип, прямоугольник, цвета, флаги) + данные типа. Обработчики — **коды
  событий** (`switch` в `handle` экрана), без указателей на функции
  (указатель на `__banked`-функцию SDCC сам не переключает банк, 4).
- **Строки** — идентификаторы-числа (конвертер генерирует `str_ids.h`),
  тексты в страницах ресурсов, выбор через окно Win3.
- **Правила** (`*.rul`) — конвертер → бинарные таблицы с индексами вместо
  строковых ключей + `rule_ids.h`. Модов нет, конфигурация одна (00).
- **Модель игры** — фиксированные массивы (баз ≤8, солдат ≤N, кораблей ≤M,
  склад — счётчики `[база][предмет]`), никаких `std::vector/map/string`.
- **Без плавающей точки**; RNG — 32-бит xorshift.
- **Сохранение** — бинарный снимок модели (десятки КБ).
- **Язык** — `en-US` (единственный в REF для xcom1); шрифты OpenXcom
  содержат кириллицу — русский возможен при наличии перевода.
- **Палитры** по экранам — из `interfaces.rul` (цвета элементов) и
  `PALETTES.DAT`/`BACKPALS.DAT`; смена — DMA RAM→CRAM.

## 4. Память: окна, страницы, банкинг — [принято]

### 4.1 Окна CPU

| Окно | Страница | Содержимое | Кэш |
|---|---|---|---|
| Win0 #0000–#3FFF | #04 «ядро / BIOS» | RST (#0000–#00FF), **ядро на ассемблере** (`_CODE`, `_HOME` — рантайм SDCC, трамплины, менеджер страниц, дальняя память, ресурсы, текст, ввод; §6.1) #0100–#37FF, стек #3800–#3DFF, векторы IM2 #3EFB | да |
| Win1 #4000–#7FFF | #05 «данные» | все переменные C (`_DATA`, `_INITIALIZED`, `_BSS`, `_HEAP`) и ядра (`_KDATA`: кольцо DMA), стартовая заглушка SPG в #7FF0 | да |
| Win2 #8000–#BFFF | банки кода | код экранов и логики (`__banked`) + их константы | да |
| Win3 #C000–#FFFF | любая | «дальние» данные: ресурсы, строки, таблицы правил, буферы | **нет** (DMA) |

Win0 и Win1 не переключаются никогда → ISR, стек, общие данные и
очередь DMA всегда доступны. Страница #05 — та, что загрузчик SPG ставит в
Win1, стартовая заглушка в её конце подключает ядро и прыгает в него.

### 4.2 Карта физических страниц (256 шт.)

| Страницы | Назначение |
|---|---|
| #00–#03 | резерв / пул (стр. #02 стоит в Win2 при старте SPG) |
| #04 | ядро (Win0) |
| #05 | данные (Win1) |
| #06–#09 | состояние кампании (через Win3): #06 `state_t`, #07 солдаты, #08–#09 резерв (12 §2) |
| #0A–#0F | резерв; #0F — под окном FMAddr (`SCRATCH_PAGE`, input.c) |
| #10–#1F | экран 256c: 512x512 (два буфера по 256 строк), выравнивание 16 |
| #20–#2F | TSU: листы спрайтов/тайлов (выравнивание 8), карта тайлов |
| #30–#4F | **банки кода** (до 32 x 16 КБ = 512 КБ) |
| #50–#AF | ресурсы (пакеты *.PAK: палитры, шрифты, фоны, строки, правила) — 96 стр. = 1.5 МБ |
| #B0–#EF | динамический пул (менеджер страниц) — 64 стр. = 1 МБ |
| **#F0–#FF** | **не трогать** (загрузчики, TS-BIOS, vDOS) |

### 4.3 Джампер (межстраничные вызовы)

- SDCC `__banked`: вызов идёт через библиотечный трамплин
  `___sdcc_bcall_ehl` (E = номер банка, HL = адрес), он вызывает наши
  **`get_bank`** (A = текущий банк, прочие регистры не трогать) и
  **`set_bank`** (A = банк; не трогать BC, DE, HL). Трамплин сохраняет
  банк вызывающего на стеке и восстанавливает при возврате, результат
  (A / DE / HL) не портится.
- Файл C целиком живёт в одном банке: `--codeseg BANKn --constseg BANKn`;
  при линковке `-Wl-b_BANKn=0xn8000` (номер банка = биты 16–23 адреса).
- `set_bank`: страница = `bank_page[банк]` (таблица в ядре, генерирует
  сборка), `OUT (#12AF)`, теневой регистр. Банки не обязаны идти подряд.
- Стоимость банкового вызова ~120–150 тактов (≈10 мкс) — нормально для
  экранов; горячие циклы держать внутри одного банка или в общем коде.
- Правила:
  1. Функции, вызываемые из других файлов, объявлять `__banked`; внутренние
     — `static`.
  2. **Не передавать указатели на константы банка A в функции банка B**
     (Win2 переключится). Общему коду — можно (банк вызывающего остаётся
     включён). Иначе — копировать в Win1 или передавать идентификатор.
  3. Никаких указателей на `__banked`-функции; нужен обратный вызов —
     дальний дескриптор `{банк, адрес}` + `far_call` ядра.
  4. ISR и всё, что вызывается из ISR, — только в общем коде (Win0).
- Упаковка файлов по банкам — таблица в `tools/build.ps1`; checkmap
  проверяет, что каждый банк ≤ 16 КБ. Позже — автоматическая упаковка по
  размерам.

### 4.3a Оверлеи: резидентная и сменная части — [принято, идея пользователя]

Как в оригинале (`GEOSCAPE.EXE` / `TACTICAL.EXE`, 06), но внутри одной
программы:

| Часть | Код | Данные |
|---|---|---|
| **Резидентная** | ядро/BIOS (Win0), виджеты, стек экранов, модель игры, сохранение/загрузка, общие утилиты | Win1 (переменные), модель кампании, общие ресурсы (шрифты, строки интерфейса, палитры) |
| **Оверлей «Геоскейп»** | экраны геоскейпа/баз/Уфопедии, время и события, (позже) карта/глобус, перехват | ресурсы экранов баз, фоны, картинки Уфопедии |
| **Оверлей «Бой»** | рендер изометрии, логика боя, ИИ, инвентарь, разбор полётов | карта боя, графика местности и юнитов миссии (большая часть пула) |

- Страницы кода делятся: **#30–#3F — резидентные банки**, **#40–#4F —
  банки оверлея** (одни и те же физические страницы для обоих режимов).
- Сборка — одна линковка, у каждого банка свой номер; банки оверлеев
  выносятся не в SPG, а в отдельные файлы (`GEO.OVL`, `BAT.OVL`) с
  таблицей «банк → страница». При смене режима ядро грузит файл оверлея в
  страницы #40–#4F (с SD, либо из копии в пуле, пока хватает памяти) и
  переписывает `bank_page[]`. Вызов банка чужого оверлея — авария (проверка
  в `set_bank` в отладочной сборке).
- Данные режима (карта боя, графика) — страницы пула, выделяемые при входе
  в режим и освобождаемые при выходе; в Win1 — только маленькие общие
  переменные. Передача «геоскейп ↔ бой» — через модель в резидентной части
  (как `MISSDAT` в оригинале, но в памяти).
- Пока всё помещается в 4 МБ, оба оверлея могут жить в памяти
  одновременно (разные страницы) — механизм оверлеев включаем, когда
  понадобится место или быстрый старт.

### 4.4 Менеджер страниц (в ядре)

- Статические зоны (4.2) задаются сборкой; динамический пул #B0–#EF —
  битовая карта занятости (8 байт).
- API (C, общий код):
  - `uint8_t pg_alloc(uint8_t n, uint8_t align)` — n подряд, с
    выравниванием (для экранов/листов TSU), `0xFF` — нет места;
  - `void pg_free(uint8_t first, uint8_t n)`;
  - `uint8_t pg_map3(uint8_t page)` — подключить в Win3, вернуть прежнюю
    (для вложенного использования: сохранить/восстановить);
  - дальние копии: `far_copy(dst_phys, src_phys, len)` через очередь DMA;
    `far_read/far_write` небольших блоков через Win3.
- Дальний адрес — 22 бита: `(страница << 14) | смещение`
  (`uint32_t`), он же формат адресов DMA.
- Страницы #F0–#FF менеджер не выдаёт никогда; mkspg предупреждает, если
  в них попадают данные.

### 4.5 Ресурсы

Каталог ресурсов (конвертер): `id → (страница, смещение, размер,
формат)`. Малые и постоянно нужные пакеты (PAL, LANG, RULES, GEO) **вшиты в
SPG** (mkspg `--data`); большие (фоны окон, картинки Уфопедии, предметы)
читаются **с SD-карты** в кэш слотов пула по первому запросу — `res_find`
спрашивает `sdres_find`, если во вшитых нет (13_sd_card.md).

### 6.2 Описание экрана

Экран — `sdef_t` (категория `interfaces.rul` для цветов, категория для
палитры, фон окна, флаги `SF_POPUP`/`SF_ALTPAL`, число виджетов) и массив
`wdef_t` по 16 байт: тип, x/y/w/h, элемент, строка (`STR_*` или `DYN(n)` —
текст даёт экран), флаги текста/виджета, действие + аргумент, клавиша.
Таблицы — константы банка экранов; `scr_get` копирует их в Win1 (ядро видит
их, когда Win2 занят шрифтом). Экраны с переменным числом виджетов
(разделы Уфопедии, переключатели графиков, цели) достраивают массив в `*_get`.

| Виджет | OpenXcom | Рисование |
|---|---|---|
| `W_WINDOW` | Window | фон экрана с отступом 5 (картинка выровнена по началу экрана), кольца c+3,c+2,c+1,c+2,c+3 |
| `W_BUTTON` | TextButton | фаска c+1/c+5/c+2/c+4, лицо c+3; нажатие — инверсия вокруг c+3 (панель геоскейпа `WF_GEO`: вокруг c+2, шрифты GEO) |
| `W_TOGGLE` | ToggleTextButton / группа | как кнопка; состояние спрашивается у экрана (`EVT_QUERY`), `act` — номер группы |
| `W_TEXT` | Text | цвет + уровень глифа, `{ALT}` (#01) — color2; перенос, центр, середина; крупный не влез — мелкий |
| `W_LIST` | TextList | строки через 8/16 точек, колонки через `\t` (ширины — `LIST_COLS`), стрелки 13x14 при переполнении, выбор строки `WF_SEL`; `LC_DOT` в выравнивании колонки — точки до её ширины (`setDot`) |
| `W_TOGGLE` нажатый | ToggleTextButton::setInvertColor | `EVT_QUERY` вернул цвет > 1: кнопка рисуется этим цветом и инвертируется вокруг цвет + 4 (графики) |
| `W_FRAME` | Frame | кольца + заливка color2 |
| `W_FILL`, `W_IMAGE` | Surface | заливка; кусок картинки (`act/arg` — начало картинки на экране / 2) |
| `W_CUSTOM`, `W_HOTSPOT` | InteractiveSurface | рисует экран (`EVT_DRAW`) / невидимая область |
| `W_ARROW` | ArrowButton 13x14 | стрелка вверх / вниз (`flags & 1`), автоповтор, как у стрелок строк |
| `W_COMBO` | ComboBox | кнопка с треугольником 11x8 в (w−14, 4); клик открывает экран 12 |

Флаги и прочее, добавленное к ядру 2026-09-15:

- `WF_THIN` (окно) — тонкая рамка-фаска списка ComboBox; `WF_RSEL` (список) —
  правая кнопка тоже выбирает строку (`ui_arrow_max = 1`; удаление сохранения).
- Маркер `\x03 c` в начале строки списка — её цвет (`TextList::setRowColor`).
- `LIST_COLS`: байт `buf[1+2n]` — смещение колонки стрелок у строк, `buf[2+2n]`
  ≠ 0 — стрелки влево/вправо (`ARROW_SMALL_LEFT/RIGHT`, снаряжение корабля).
- Автоповтор стрелок при удержании левой кнопки: 13 кадров, затем каждые 3
  (Timer 250/50 мс OpenXcom).
- **ComboBox** (`combo_t combo` в `screens.c`): экран-владелец заполняет
  `x, y, w, h, bg, ui, el, n, item[16]` и открывает `SCR_COMBO` (12, банк 2);
  тот строит окно `WF_THIN` и список до 10 строк под кнопкой, клик — `combo.sel`,
  `combo.changed = 1`, клик мимо / ESC — закрыть. Владелец видит `changed` в
  своём `*_get` при перерисовке.
- `SF_RAWPAL` (экран): палитра — ресурс `palui` без BACKPALS; `EL_RAW + n` —
  цвета из `ui_raw[16][2]` (статьи Уфопедии задают палитру и цвета числами).
- `A_POPN` — снять N экранов.
- **Невыделяемый список щелчок не держит** (как TextList): у статей построек и
  USO список характеристик по высоте заходит на кнопки `<< >>` — раньше щелчок
  по «>>» съедал список.
- **Частичная перерисовка:** `ui_dirty(slot)` — после текущего события или тика
  перерисовать только виджеты DYN-слота (0..63); `ui_dirty_row(slot, row)` — одну
  строку списка (восстановление полосы строки + `draw_row`, до 8 строк, больше —
  весь список). «Вернуть 1» из `EVT_*` и `A_DYN` по-прежнему перерисовывают все
  DYN-виджеты — оставлять только для смены состава экрана. Правило (наставление
  пользователя): перерисовывать только изменившееся, без фанатизма. Переведены
  часы геоскейпа, стрелки покупки/продажи/перевода, снаряжения, исследований и
  производства, подсказка базы (14_todo.md §1.1).
- **Наведение мыши:** событий движения нет — экран опрашивает `cursor_x/y` в
  `EVT_TICK` (верхнему экрану каждый кадр). Так сделаны рамка габаритов постройки
  (`BaseView::setSelectable/blink`: 1 точка, `basescape.baseView.color2`, мигание 5
  кадров, точки под рамкой сохраняются и возвращаются) и подсказка над видом базы
  (`viewMouseOver`: постройка, у ангара — корабль).
- `ui_color_in(категория, элемент, n)` — цвет элемента чужой категории
  (`State::add(surface, id, category)`): вид базы в окне установки берёт цвета
  `basescape` (раньше дни стройки рисовались цветом 0).

События экрана: `EVT_OPEN`, `EVT_BUTTON` (arg виджета), `EVT_LIST` (строка),
`EVT_CLOSE`, `EVT_TICK` (каждый кадр верхнему экрану; 1 — перерисовать
`DYN`-виджеты), `EVT_DRAW`, `EVT_QUERY`, `EVT_KEY` (клавиша без виджета —
ввод имени базы). Обработчик не трогает стек сам, а оставляет запрос
`UI_GO(действие, аргумент)`: `A_POP`, `A_PUSH`, `A_SET`, `A_POP_PUSH`,
`A_POP2`, `A_REDRAW`, `A_DYN` — ядро выполняет его после возврата.

Стек: всплывающий экран рисуется поверх; после закрытия перерисовывается
всё от последнего полноэкранного (полноэкранный сначала чистит экран).
Палитра — всегда верхнего экрана: палитра категории (или родителя, иначе
PAL_GEOSCAPE) + блок BACKPALS из элемента `palette` (`color`, при alterPal —
`color2`), как `State::setInterface`.

Ввод: клик — сверху вниз по виджетам (как в OpenXcom), клавиши виджетов
(`SPACE`/`BREAK` = ESC, `ENTER`, буквы, цифры: `I B G U F`, `1`–`6` на
геоскейпе). Нажатия защёлкивает кадровое прерывание (`input_isr`).
Окно открывается и снаружи: `poke _ui_request <номер>`.

### 6.4 Отличия от OpenXcom (пока)

- Нет анимации открытия окон (`POPUP_*`) и звуков.
- Нет подсветки строки списка под курсором (selector) и полосы прокрутки.
- TextEdit (`W_EDIT`, текст в `ui_edit`, `arg` — длина): буквы, цифры,
  пробел, `CS+0` — удалить; без курсора внутри строки.
- Позиции/размеры элементов из `interfaces.rul` (`pos/size` с родителем) не
  конвертируются; у Dogfight раскладки UFO и TFTD (кнопки, дистанция, вид НЛО)
  заданы в `scr_dogf.c` таблицами.
- Текст тревоги миссии — `alienDeployments.alert` (TFTD: «ALIENS LAUNCH PORT ATTACK
  ON …»), фон — `alertBackground`.
- Переключатели графиков рисуются обычной инверсией (без `setInvertColor`).

### 6.5 Скорость (эмулятор, 14 МГц + кэш)

Замеры — строки `ui: screen N, K frames` и профилировщик (07 §6).

| Шаг | Было | Стало | Что сделано |
|---|---|---|---|
| Геоскейп (полная перерисовка) | 85 кадров | 28 | глобус-заглушка без умножений и через memset; заливки без 32-битной арифметики |
| Финансы (17 строк x 3) | 84 | 34 | глифы — ассемблер `glyph.s` (самомодификация цвета, пропуск пустых байт); `fmt_num` вычитанием степеней 10 |
| Весь автотест | 7696 | 2848 | + защёлка ввода в прерывании, кэш `res_find` |

Остаётся медленным вывод текста (~1/3 времени) и заливки мелких кнопок.
Дальше: **кэш глифов + DMA BLT1** (глиф, раскрашенный под цвет, один раз
рисуется в страницу пула, дальше копируется блиттером с прозрачностью; нечётный
x — вторая копия со сдвигом, т.к. DMA работает словами), `gfx_map` и
`cpu_column` — на ассемблере, перерисовка только изменившихся текстов часов.

### 6.6 Идея пользователя: тайловый экран

«Если положение и размеры кнопок кратны 8, можно использовать тайловый
экран» (TSU: тайлы 8x8, 4 бит/точка, палитра — любой блок из 16 цветов, то
есть 5 оттенков кнопки + текст в него укладываются). Разбор раскладок
OpenXcom: координаты **не** на сетке 8 — кнопки меню 92x20 в (64,90),
панель геоскейпа 63x11 с шагом 12 в x=257, окна 256x160 в (32,20) с
кольцами по 1 точке, тексты с y=45, 53, 69 и т.д.; шрифты пропорциональные.
Двух слоёв тайлов (у каждого свой сдвиг) не хватит на все смещения по
модулю 8. Поэтому основной слой остаётся растровым 256c — картинка 1:1 с
оригиналом. Аппаратные слои применяем там, где сетка не нужна или своя:
курсор уже спрайт TSU; кандидаты — глобус и радар (свой слой тайлов/спрайтов
поверх фона), окно Dogfight, метки целей (спрайты), а для текста — кэш
глифов с DMA (6.5). Если какой-то экран всё же захочется перевести на
тайлы (например, собственные окна вроде опций), его раскладку можно
выровнять на 8 без ущерба для узнаваемости.
