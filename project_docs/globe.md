# Глобус: аудит и план быстрого рендера

Документ 2026-09-15. Задача пользователя: «глобус должен получиться живчик» — разобрать,
как рисует OpenXcom, что даёт железо TS-Config, предложить методики с цифрами и
выбрать путь. Код в `src/` по этому документу ещё не писался. Все цифры замеров —
скрипты Node `tmp/globe_research/analyze*.js` (раздел 12), картинки-сравнения —
`tmp/globe_research/png/`.

**Статус реализации (2026-09-15):** этап 0–1 сделан, рендер — **М4в** (рёберный, §5.4 с
предрасчётом в конвертере). Ресурс `GLOBE` v5 (09 §7) — не многоугольники, а плоская карта:
WORLD.DAT перекрывается (TFTD ~5% точек сферы, OpenXcom рисует по порядку) и имеет
почти-T-стыки, поэтому конвертер пересекает все рёбра, красит стороны кусков по правилу
«последний содержащий» и оставляет только границы смены текстуры (TFTD 1298 рёбер, UFO
1197), плюс сетка 5° на случай «в окне нет рёбер». Движок `src/ui/globe.c` + `globe_s.s`
(банк 24; точки и клики — `globe_ui.c`, банк 2): проекция вершин таблицами произведений
(8 констант вида, §6.2 заменён), рёбра с отсечением по горизонту и окну, строки по списку
активных рёбер (слоты, порядок по x, сортировка с допуском и починка кучек почти совпавших
рёбер по согласованности текстур, «события» левого края для строк без рёбер), отрезки
DMA по 3 записи в порты. Проверка — `tools/globe_model.js` (модель против эталона «художник
по многоугольникам») и `tools/globe_emucmp.js` (снимок эмулятора против эталона): совпадение
до 1 пары пикселей на границах, у края диска на зумах 0–1 — z в Q12 и вставка в кучку рёбер по текстурам. Скорость (кадров на рендер, зумы 0–5): **23/20/12/7/5/5**
(М4а — 45–49/46/23/16/9/8, первая версия на C — 260 на зуме 0); смена набора узоров
(зумы 1→2, 3→4) — прямыми DMA, +7 кадров. Раскладка — `tools/globeprof.ps1`. Следующие
этапы — тень (§6.4), метки, оверлеи (14_todo §4).

## 0. Итог в одном экране

**Рекомендация — метод М4 (§5.4, §6):** геометрия как у OpenXcom (многоугольники
`WORLD.DAT`, ортографическая проекция, любой наклон), но растеризация не попиксельно,
а **отрезками строк**, которые выводит **DMA**:

1. вершины проецируются таблицами (8-битные умножения квадратами на зумах 0–1,
   16-битные на 2–5; при вращении по долготе — только 2 умножения на вершину);
2. многоугольники заливаются активным списком (Брезенхем/ЦДА по рёбрам), отрезки
   строк сортируются и склеиваются;
3. **узор суши привязан к экрану** (так в OpenXcom: `texturedPolygon(…, 0, 0)`), поэтому
   отрезок суши — это копия куска заранее развёрнутой строки узора; окно глобуса
   шириной ровно 256 даёт трюк «младший байт источника = x»: на отрезок — **3 записи
   в порты DMA** (§6.5);
4. тень день/ночь — **вторым проходом DMA BLT2** (сложение по полубайтам с насыщением —
   это ровно `getLandShadow` OpenXcom), полосы уровней считаются эллипсами по строкам
   (приращениями, без умножений), океан — 11 уровней;
5. сборка в невидимых строках экрана 280–479, копия на экран одним 2D-DMA по кадровому
   прерыванию (без разрыва), метки и надписи — поверх, восстановление — из заднего буфера;
6. перерисовка **только по причинам**: поворот/зум/центр — полный рендер; сдвиг тени —
   рендер из кэша отрезков геометрии; НЛО и мигание — только метки 3x3.

Цифры (модель тактов §5, ±30 %, асм-версия горячих мест):

| | Зум 0–1 (шар) | Зум 2–3 | Зум 4–5 |
|---|---|---|---|
| полный рендер с тенью | 4.3–5.8 кадра (8–11 к/с) | 2.6–5.3 | 0.6–3.8 |
| вращение (без прохода тени) | 2.2–3.5 кадра (14–22 к/с) | 1.0–2.5 | 0.5–1.9 |
| сдвиг тени (кэш геометрии) | ~3 кадра | ~2–3 | ~1–2 |
| неподвижный глобус, движутся НЛО | < 0.02 кадра на такт | | |
| первая версия на C | 10–20 кадров | | |

Память: код — 2 новых банка (#47, #48); данные в SPG (`GEO.PAK`) +~65 КБ
(4 страницы из 54 свободных в #7A–#AF); при геоскейпе — 10–12 страниц пула (узоры 8,
константы тени 1, рабочие 1–2, кэш отрезков 1), освобождаются на время боя. Win1 — не
больше ~100 байт.
Диск (SD) не нужен. Цель по железу — плата VDAC: BLT2 в прошивке есть только в сборках
VDAC (`XTR_FEAT`, §3.2); без неё тень считает процессор по таблице (+1.2 кадра на зуме 0).

Ограничивать наклон глобуса ради скорости **не нужно**: метод «строка = параллель»
(М3, только наклон 0) быстрее всего на 10–16 % на зумах 0–1, а на 2–5 — на 0–8 %
(§5.3). Отдельный «плоский» режим для крупных зумов тоже не нужен: М4 там дешевле всего,
а синусоидальная карта искажает на 7–50 пикселей (§5.3).

## 1. Что рисует OpenXcom (аудит)

Источник — `REF/OpenXcom/src/Geoscape/Globe.cpp` (далее `G:строка`), `Globe.h`,
`Mod/RuleGlobe.cpp`, `Mod/Mod.cpp`, `Geoscape/GeoscapeState.cpp`, правила
`REF/OpenXcom/bin/standard/xcom1|xcom2/globe.rul`, `regions.rul`, `countries.rul`.

### 1.1 Окно, зум, проекция

- Глобус — поверхность 256x200 в (0, 0), центр (128, 100): `GeoscapeState.cpp:127`
  (`screenWidth − 64`). У нас то же (`src/ui/scr_geo.c:239`, `W_CUSTOM` 256x200).
- Радиусы 6 зумов `G:1885` `setupRadii`: 0.45/0.60/0.90/1.40/2.25/3.60 × 200 =
  **90 / 120 / 180 / 280 / 450 / 720**. С зума 2 диск (R = 180 > √(128² + 100²) = 162)
  закрывает всё окно — дальше «полноэкранный» режим, горизонта не видно.
- Ортографическая проекция `G:332` `polarToCart`:
  `x = cx + R·cosφ·sin(λ−λ0)`, `y = cy + R·(cosC·sinφ − sinC·cosφ·cos(λ−λ0))`,
  C — широта центра (наклон). Широта OpenXcom: минус — север (у нас так же, `geo.c:5`).
  Обратная — `G:355` `cartToPolar` (asin/atan2), задняя сторона — `G:389` `pointBack`.
- Наклон **не ограничен** (`G:868`, `G:640`): глобус можно перевернуть через полюс.
  Наша заглушка ограничивает ±90° (`scr_geo.c:360`).
- Вращение `G:865`: шаг `ROTATE_LONGITUDE 0.10` / `ROTATE_LATITUDE 0.06` рад ×
  `(110 − geoScrollSpeed)/100` / `(zoom + 1)` за срабатывание таймера 10 мс (`G:285`);
  при `geoScrollSpeed` = 20 (`Engine/Options.cpp:136`) это **5.2° долготы на зуме 0**,
  2.6° на зуме 1 … 0.86° на зуме 5. Правая кнопка — центр на точку (`G:1794`),
  перетаскивание — `G:1601`. Кнопки вращения и зума — `GeoscapeState.cpp:145–149`
  (у нас `GLOBE_HOTSPOTS`, `src/ui/scrdef.h:48`).
- Эффект наезда перед воздушным боем `G:585` `zoomDogfightIn`: 10 шагов радиуса
  `(R3 − R0)/10` = 19 пикселей до зума 3 (`DOGFIGHT_ZOOM`, `Globe.h:49`), обратно —
  `zoomDogfightOut`.

### 1.2 Суша и вода

- `WORLD.DAT` — записи по 20 байт: 4 пары долгота/широта в 1/8°, `value[6] = −1` —
  треугольник, `value[8]` — текстура (`RuleGlobe.cpp` `loadDat`, `fmath.h:85`).
- Каждая перерисовка: `cachePolygons` (`G:765`) при сдвиге вида — отсев задних
  (`−furthest > closest` по z вершин, `G:799`) и проекция каждой вершины каждого
  многоугольника в `double` (вершины не общие — 2.4–2.9 тыс. проекций); затем
  `drawLand` (`G:912`) — `drawTexturedPolygon(x, y, n, frame, 0, 0)` (`G:926`,
  `Engine/Surface.cpp:780` → SDL_gfx `texturedPolygon`,
  `deps/include/SDL/SDL_gfxPrimitives.h:216`).
- **Узор привязан к экрану**, а не к карте: смещение текстуры (0, 0) — пиксель (x, y)
  берёт `TEXTURE[y mod 32][x mod 32]`. При вращении контуры суши едут, а узор под ними
  стоит. Это главное свойство для нас (§4).
- `TEXTURE.DAT` — 39 кадров 32x32 = 13 текстур × 3 масштаба; набор по зуму
  `_zoomTexture = (2 − ⌊zoom/2⌋)·13` (`G:517`): зумы 0–1 — кадры 26–38, 2–3 — 13–25,
  4–5 — 0–12.
- Фон диска — `drawOcean` (`G:897`): круг цвета `OCEAN_COLOR` = блок `oceanPalette`
  (UFO 12 → 192, TFTD 1 → 16; `globe.rul:3`, `RuleGlobe.cpp:136`). В UFO многоугольники —
  суша, в TFTD — вода, а «океан» диска — суша (14_todo §4).
- Отрицательные номера текстур (TFTD −1…−4) и выбор местности боя по текстуре —
  `globe.rul` `textures`, `G:1826` `getPolygonTextureAndShade`; для рисования достаточно
  номера кадра.

### 1.3 Тень день/ночь

- `drawShadow` (`G:986`) — **для каждого пикселя окна** (51 200): нормаль сферы из кэша
  `_earthData` (`G:1904`, по зуму), направление на солнце `getSunDirection` (`G:936`:
  время суток, сезоны — опция `globeSeasons`, по умолчанию выкл., `Options.cpp:180`),
  шум 0..3 из поля 60x60 (`G:296`).
- `getShadowValue` (`G:176`): `t = (|e − s|² − 2)·125 = −250·(e·s)`; t < −110 →
  день (−31), t > 120 → ночь (50), иначе таблица `shade_gradient` (`G:118`, 240
  значений, нелинейная, 0..35); минус шум, зажим 0..31. Полоса терминатора —
  e·s от +0.44 до −0.48, то есть **~55° дуги**: на зуме 0 — до 90 пикселей, на зумах
  3–5 часто всё окно.
- Океан: `OCEAN_COLOR + тень` (32 цвета, `G:203`). Суша: `getLandShadow` (`G:208`):
  `e = dest + тень/3`, но не дальше конца группы из 16 цветов (`ColorShade` 15).
  Замер палитр: у UFO 192..223 — плавный градиент (0,9,29) → (0,4,14) (6 бит, соседние
  цвета отличаются на ~0.5 единицы), у TFTD 16..47 — (38,43,0) → (21,14,0). Узоры суши
  лежат в группах по 16, младший полубайт ≤ 7 (все 39 кадров обеих игр) — «+10 с
  насыщением на 15» не выходит из группы.

### 1.5 Как часто OpenXcom перерисовывает

`GeoscapeState::timeAdvance` вызывает `_globe->draw()` на **каждом такте** (80 мс,
`GeoscapeState.cpp:684`), вращение — таймер 10 мс; `draw()` (`G:877`) каждый раз
рисует всё: океан, сушу, радары, пути, тень по всем пикселям, метки, детали. Кэш —
только проекция многоугольников и нормали.

### 1.6 Объём вычислений OpenXcom и почему «в лоб» на Z80 нельзя

На кадр (зум 0, UFO, вид на Европу): ~2.9 тыс. проекций вершин (по 4 тригонометрии в
`double` + ещё 3 на отсев), заливка ~15 тыс. пикселей суши, **51 200 пикселей тени**
(вектор, 3 квадрата, таблица, зажим), метки, границы.

На Z80 (такты 14 МГц):
- программная плавающая точка: ~20–50 тыс. тактов на sin → ~17 тыс. вызовов ≈
  500 млн тактов ≈ **30 с на кадр**;
- «в лоб», но в фиксированной точке (Q14, таблицы sin, умножение 16x16 ~200 тактов):
  вершины 2.9 тыс. × ~1.5 тыс. = 4.4 млн, тень 51 тыс. × ~150 = 7.7 млн, заливка
  ~0.75 млн → **~45 кадров (≈1 с) на одну перерисовку**, а OpenXcom перерисовывает
  12.5 раз в секунду.

Нужны три вещи: (1) не считать попиксельно ни проекцию, ни тень; (2) двигать пиксели DMA;
(3) не перерисовывать без причины.

## 3. Бюджеты железа и памяти

### 3.1 Процессор

- Кадр 71 680 тактов 3.5 МГц → **286 720 тактов на 14 МГц**, 48.83 Гц
  (02 §2, `REF/Unreal`: `unreal/Unreal/machine/z80main.cpp:118–156`).
- Кэш 512 байт прямого отображения; включён для Win0–Win2 (`src/kernel/boot.c:101–102`),
  Win3 — без кэша (туда пишет DMA). Промах: M1 7–8 тактов вместо 4, чтение 5–6 вместо 3
  (`z80main.cpp:124`, `:147`). Код рендера — в банке (Win2, кэш), данные вершин и
  рабочие массивы — через Win3 (+2–3 такта на чтение).
- Доступно глобусу ~90 % кадра (~258 тыс. тактов): прерывание кадра (защёлка ввода,
  счётчик), будущий плеер музыки (худший кадр ~6 тыс., 09 §7), ход времени — раз в
  5 кадров (на «1 дне» 20–80 кадров на игровой день, 14_todo §3).
- Такты команд (Z80): `LD r,(HL)` 7, `LD (HL),r` 7, `ADD HL,DE` 11, `EXX` 4,
  `OUT (C),r` 12, `OUTI` 16, `IN r,(C)` 12, `LDI` 16, `LDIR` 21/байт, `DJNZ` 13,
  `JR` 12/7, `PUSH` 11, `POP` 10, `LD r,(IX+d)` 19. Умножение 8x8 по таблице
  квадратов (`a·b = q(a+b) − q(a−b)`, q(n) = ⌊n²/4⌋, таблица 1 КБ) — ~50–60 тактов;
  16x16 → старшие 16 — ~150–200.

### 3.2 DMA

- Режимы и цены (циклов DRAM 7 МГц на слово): RAM→RAM 2, BLT1 (пропуск нуля) 3,
  **BLT2 (dst = src + dst, байты или полубайты, OPT — насыщение)** 3, FILL 1
  (02 §6; `REF/fpga/common/dma.v:199–204` — у блиттера три фазы: чтение источника,
  чтение приёмника, запись).
- Свободно для DMA при 320x200 256c — ~111 тыс. циклов на кадр: **~111 КБ копии,
  ~74 КБ BLT, ~222 КБ заливки** (02 §6). Процессор не останавливается.
- Адрес — 22 бита по словам; **чётные x и длины** (DMA игнорирует бит 0, 02 §11.12).
  После передачи регистры указывают за конец; запись `DMASAddrH` меняет только биты

- **BLT2 есть не во всех прошивках**: `dma.v:88–90`, `:157–183` — под `ifdef XTR_FEAT`;
  `XTR_FEAT` включён в `REF/fpga/quartus_vdac/tune.v:16` и `quartus_vdac2/tune.v:17`,
  выключен в `REF/fpga/quartus/tune.v:18` («extra features, in only IDEless version»).
  **Целевое железо с VDAC (CLAUDE.md) — BLT2 есть**; эмулятор реализует его всегда
  (`unreal/Unreal/devices/tsconf/tsconf.cpp:266–324`). Без VDAC — запасной путь §6.12.
  *(Факт стоит перенести в 02 §6.)*
- С ALGN при ASZ = 0 шаг строк 256, а не 512 — для BLT2 по полубайтам на экране 256c
  выравнивание не использовать (по строке — отдельный запуск).

## 4. Ключевые наблюдения (на них стоит план)

1. **Узор суши экранный** (§1.2). Кусок строки y узора t на [x0, x1) — это байты
   `strip[t][y & 31][x0..x1)` строки узора, повторённой до ширины 256. Проецировать
   текстуру не нужно; нужна только **геометрия границ** и копия отрезков.
2. **Окно глобуса — ровно 256 пикселей.** Если строки узоров лежат блоками по 256 байт,
   смещение в блоке = x. После копии отрезка регистр источника DMA указывает на
   `блок + x1` — начало следующего отрезка, но в «чужом» блоке; достаточно сменить
   `DMASAddrH` (номер блока). Приёмник продолжается сам. **3 записи в порты на отрезок.**
3. **Тень суши = сложение полубайта с насыщением** — ровно режим BLT2 (ASZ = 0, OPT = 1):
   `dest & F0 | min(15, (dest & 0F) + k)` = `getLandShadow` при k = тень/3 (§1.3).
4. **Уровни тени — полосы.** Тень зависит только от e·s (нормаль · солнце). Граница
   уровня на сфере — малый круг вокруг подсолнечной точки, на экране — эллипс; в строке
   каждый уровень занимает ≤ 2 отрезка, вдоль строки уровень — «ложбина» (убывает, потом
   растёт). Считать надо **границы полос**, а не пиксели.
5. **Океан без узора**: его пиксель зависит только от уровня тени — отрезки океана
   дробятся лишь на границах полос. Градиент очень пологий → 11 уровней вместо 32
   неотличимы (превью `tmp/globe_research/png/*_port11.png` против `*_ref.png`).
6. **Почти всё время глобус неподвижен.** Дорогой случай один — вращение (и наезд перед
   боем). Сдвиг тени на обычных скоростях — раз в секунды; движение НЛО — метки 3x3.
7. **Параллели.** При наклоне 0 строка экрана — параллель: `y = R·sinφ`. Тогда все
   границы строки — это долготы из заранее готового списка (конвертер), x = R·cosφ·
   sin(λ−λ0) — одно умножение на границу. Это самый дешёвый поиск границ, но только при
   наклоне 0 (§5.3).
8. **Наклон не ломает М4.** Стоимость М4 от наклона не зависит; ограничение наклона
   даёт выигрыш только методу М3.

## 5. Методики рендера (сравнение)

Модель стоимости (`analyze2.js`, `analyze3.js`): такты на операцию асм-версии —
проекция вершины 250 (8 бит) / 700 (16 бит) / 110 (приращением при вращении),
установка многоугольника 160, шаг ребра 45, запись и сортировка отрезка 75, событие
«параллели» 120, эллипс уровня на строку 60, вывод отрезка проход 1 — 150, проход 2 —
110, накладные строки 250. Кадр = 258 тыс. тактов. Точность модели ±30 %; её надо
проверить профилировщиком на этапе 1 (§9).

### 5.1 М1. «В лоб» в фиксированной точке — отказ

Попиксельная тень + проекция каждой вершины 16x16: ~45 кадров на перерисовку (§1.6).
Точность 1:1, память ~0. Годится только как эталон.

### 5.2 М2. Растровый глобус по таблицам обратной проекции — отказ (как основной)

Для каждого пикселя диска заранее (конвертер) — (φ, Δλ) при данных зуме и наклоне;
при повороте по долготе Δλ + λ0; текстура — из растровой карты мира (как WORLDMAP:
1° + 1/8° у берегов, `tools/OxzConv/Core/WorldMap.cs`), цвет — из экранного узора.

- Такты: ≥ 60–80 на пиксель (2 выборки таблицы, выборка карты с разбором граничной
  клетки, узор, тень) → зум 0: 25 тыс. пикс. ≈ **6–8 кадров**, зумы 2–5: 51 тыс. ≈
  **12–16 кадров**. Не зависит от сложности берега — но всегда медленно.
- Память: 2 байта на пиксель на (зум, наклон): 50–100 КБ; с наклонами — мегабайты
  (19 наклонов × 6 зумов ≈ 11 МБ) → только наклон 0 или SD.
- Точность: берег с шагом 1/8° (на зуме 5 — 1.6 пикс.), лесенкой.
- Плюс: можно привязать узор к карте (едет с сушей) — это уже не OpenXcom (открытый
  вопрос 7).

### 5.3 М3. «Строка = параллель» (наклон 0) + «плоский» режим крупных зумов — запасной

Наклон всегда 0: строка y — параллель φ = asin((y−cy)/R). Конвертер даёт для каждой
широты 1/8° список границ «долгота → текстура» (растр 1/8°: 65 КБ UFO / 88 КБ TFTD;
упаковка «12 бит долготы + 4 бита текстуры» — 45 / 60 КБ + смещения строк 2.9 КБ).
В кадре: для строки — границы в видимом диапазоне долгот → x = R·cosφ·sin(λ−λ0)
(таблица sin + умножение 8x8), дальше тот же вывод отрезков, что в М4. Тень — по той же
параллели: границы уровней λs ± acos(t_k / cosφ) (таблица на широту).

- Такты (зум 0–1): **3.7–4.3 кадра с тенью**, событий 1.2–2.3 тыс. на кадр; М4 на тех
  же видах — 4.3–4.8. Выигрыш 10–16 %, на зумах 2–5 — 0–8 % (там всё решает вывод).
- Цена: **наклона нет** — Европа и Северная Америка у верхнего края сплющены
  (`tmp/globe_research/png/UFO_z0_tilt0.png` против `UFO_z0_10_-45_ref.png`).
- «Плоский» режим для зумов ≥ 3 со свободной широтой центра: строка — параллель
  φ = φ0 + (y−cy)/R, x = cx + R·cosφ·(λ−λ0) (локальная синусоидальная). Тот же код
  событий, без синусов. Но это другая проекция. Смещение против ортографии OpenXcom

### 5.5 М5. Кэш отрезков для дискретных видов на SD — не нужен

Конвертер заранее считает списки отрезков геометрии для сетки видов (зум 0: 128 долгот ×
13 наклонов = 1152 вида × ~4 КБ ≈ 4.6 МБ; с шагом наклона 5° — 18 МБ), рендер только
читает (8 секторов на кадр) и выводит. Экономит проекцию и заливку (~40 % на зумах 0–1),
но: вид «щёлкает» по сетке, центр на произвольную точку (`center`) — только ближайший
вид, на зумах ≥ 2 сетка взрывается (шаг должен падать как 1/R), тень всё равно
считать. Вывод (главная статья) не сокращается.

### 5.6 М6. Предрендер кадров — отказ

Кадр зума 0 — 25 КБ; 128 долгот × 13 наклонов × 6 зумов (с шагом 1/R) — десятки–сотни
МБ, плюс тень меняется со временем. 14_todo §4: «~16 МБ только на зум 0».

### 5.7 М7. Тайлы и спрайты TSU

- Суша тайлами — нет: тайлы 8x8 целиком, 4 бита на точку (одна палитра из 16 на тайл),
  границы суши произвольные.
- **Метки** — да, как вариант: спрайты 8x8 с видимыми 3x3, мигание — сменой 1–2 цветов

- **Оверлеи** (границы, подписи, радары, пути) — тайловый слой как 4-битный битмап 1:1

## 6. Рекомендованная архитектура (М4)

### 6.1 Конвейер полного рендера

```
вид (λ0, C, R, набор узоров), солнце s
 ├─ 1. отсев ячеек 30° (72 проверки)            — вершины только видимых ячеек
 ├─ 2. проекция вершин → (x, y, видимость)        — 8 бит (зум 0–1) / 16 бит (2–5)
 ├─ 3. многоугольники: отсев (как G:799), сортировка по верхней строке
 ├─ 4. строки сверху вниз:
 │     активный список → отрезки (x0, x1, t) → сортировка, склейка, дыры = океан
 │     эллипсы уровней тени → границы полос в строке
 │     слияние → проход 1 (копия узоров, океан по полосам) → DMA
 │                проход 2 (BLT2 +k по полосам)            → DMA
 ├─ 5. копия заднего буфера (строки 280–479) → экран, по кадровому прерыванию
 └─ 6. оверлеи: радары, пути, границы, подписи, города, метки
```

Отрезки геометрии строк (выход шага 4 до слияния с тенью) сохраняются — «кэш
геометрии» (1 страница): при сдвиге только тени шаги 1–3 не повторяются (§6.8).

### 6.2 Проекция вершин

Данные вершины (конвертер + пересчёт при смене зума/наклона, рабочая страница):
долгота `u16` (65536 = 360°), `A = R·cosφ`, `K1 = R·cosC·sinφ`, `K2 = R·sinC·cosφ`,
порог видимости `T = −tgC·tgφ` (z > 0 ⇔ cos Δ > T).

На кадр при вращении по долготе (A, K1, K2, T не меняются):
```
Δ = lon − λ0                  ; 16 бит, индекс — старшие 10 бит (0.35°)
s = SIN[Δ], c = COS[Δ]        ; Q7 (зумы 0–1) / Q14 (2–5)
видима = c > T
x = cx + A·s,  y = cy + K1 − K2·c
```
2 умножения + 2 выборки ≈ 250 тактов (8 бит, погрешность ≤ 0.4 пикс. при R ≤ 120)
или ~700 (16 бит). При смене наклона/зума A, K1, K2, T пересчитываются (5 умножений на
вершину, один раз). Ещё быстрее при вращении с постоянным шагом — поворот (u, v) =
(A·cosΔ, A·sinΔ) приращениями «алгоритм Мински» (`v −= ε·u; u += ε·v`, ε = 2⁻ᵏ —
только сдвиги): ~110 тактов, сброс погрешности — точной проекцией при остановке.

Отсев: вершины разложены конвертером по ячейкам 30° (12 × 6); ячейка видна, если её
центр z > −0.36 (запас на радиус ячейки ~21°) и на зумах ≥ 2 — её проекция задевает
окно. На зумах 4–5 остаётся 10–70 многоугольников из 700 («двухуровневое дерево»;
глубже не нужно — многоугольники не перекрываются, порядок не важен).

### 6.3 Многоугольники и строки

- Отсев многоугольника — как `G:799`; вне окна — пропуск.
- Многоугольник (≤ 4 вершины, выпуклый): вершины по y, левая и правая цепочки, шаг x
  по строке в 8.8 (`ADD HL,DE` 11 тактов; наклон ребра — одно деление или таблица
  1/dy); правило пикселя — как SDL_gfx (`analyze.js` `fillPoly`), чтобы стыки совпали.
- Порядок — по строкам: многоугольники отсортированы по верхней строке (корзины по y),
  активный список ≤ 64 записи по ~12 байт (страница банка); отрезки строки — сортировка
  вставками (порядок почти не меняется от строки к строке), склейка соседних отрезков
  одной текстуры, промежутки — океан. Перекрытия (редко, округление) — побеждает
  многоугольник позже в файле, как у OpenXcom.
- Горизонт (зумы 0–1): строка рисуется в пределах полуширины диска `ρy` (таблица на
  зум, 200 значений; для промежуточных радиусов наезда — приращениями, как в заглушке
  `scr_geo.c:307`). Вне диска задний буфер не трогается: он заполнен фоном GEOBORD один
  раз при смене зума.

### 6.4 Тень

**В движке — ступенчато, блоками 8x4 (2026-09-16, `globe_sh.c`, `globe_sh_s.s`, банк 25).**
Оригинал тоже рисовал тень ступенями, поэтому точные границы уровней (эллипсы по строкам,
коммит 07b3891: ≤ 2% пар мимо, но +20…30 кадров на рендер) заменены сеткой блоков 8x4
пикселя (32 x 50): уровень блока — по его центру, 2t = TX[столбец] + TY[строка блоков] +
TZ[z центра] (лестницы на кадр без умножений, z центров — таблица `sh_z8` по зумам, четверть
диска зеркально, копия строками по 16 в страницу тени), уровень — таблица по 2t + 128.
Уровни считаются через столбец, промежуточный блок между равными соседями берёт их
уровень (e·s вдоль строки унимодальна). Подкладка — одно 2D DMA на отрезок равных уровней
строки блоков: 8 пачек (L и O четырёх строк) из образца уровня — 4 строки по 512 байт (L,
O через 256), 11 уровней = 22 КБ, 2 страницы; внутри пачки с ALGN и ASZ = 0 адрес
заворачивается в своих 256 байтах (`REF/fpga/common/dma.v:329–334`), так что сдвиг шума
по строке блоков не выходит за строку образца. Края диска на зумах 0–1 (строки блока разной
ширины, вне общей части [max pl, min pr]) — построчно, 2 пачки. Модель — `globe_shadow.js`
`BLOCK=8x4` (варианты `NONOISE`, `OCEAN32`). Кадров на рендер с терминатором в окне
(`tools\globeprof.ps1 -Hour 18`): **29/29/19/13/12/11** по зумам 0–5 (точные эллипсы —
52/53/44/26/24/23). Остаток цены тени на зуме 5 (~4.7 кадра): DMA подкладки (объём —
2 байта на пиксель диска), уровни блоков (~320 тактов на блок), медленный путь вывода
строк с тенью.

**Проверено моделью (`tools/globe_shadow.js`, 2026-09-15).** (1) Уровни k по строкам из
эллипсов совпадают с попиксельной тенью OpenXcom без шума точно (0 из 1.5 млн пар), если
порог уровня брать как у `(Sint16)` — усечение к нулю: для T ≤ 0 граница t > T − 1.
(2) Вывод «подкладка + BLT2»: строка экрана заранее заливается добавками суши
L_k(x) = ⌊(v_k − n)/3⌋ (v_k = 3k + 1, k = 10 — 31; n — шум 0..3 строки-образца со сдвигом по
строке), суша кладётся BLT2 по полубайтам с насыщением (узор + L = ровно `getLandShadow`),
океан — копией из строки O_k(x) = OCEAN + (v_k − n) (строка океана полосы узоров,
пересобранная для строки экрана); на картинках не отличить от OpenXcom (средняя разница
0.2–1.2 шага палитры). (3) Границы уровней точной формулой (корень на строку и уровень) —
сотни тысяч тактов на кадр; дёшево: круги уровней неподвижны на сфере при данном времени —
ломаная из N вершин на круг, отсечение горизонтом, пересечения со строками как у рёбер;
пересечение задаёт сторону ночи по направлению хода (ночь справа на сфере, если
(U × V)·s > 0; на экране с y вниз — зеркально), до первого и после последнего пересечения —
точный уровень первой и последней пары строки (одна выборка на край). N = 48: зум 0 — 0.7%
пар мимо на 1 уровень, зумы 1–5 — < 0.6% (N = 24 достаточно для зумов 3–5). Интервалов
уровней после округления до пар — в среднем 1200–1600 на кадр на зумах 0–2 (до 2200):
по одной DMA на интервал — нижняя граница цены (~100–150 тыс. тактов в худших видах).

**Уровень** k = ⌊тень/3⌋ ∈ 0..10 (без шума). Границы уровней в терминах d = e·s —
константы (из `shade_gradient`, конвертер или таблица в коде, 10 порогов t_k).

**Эллипсы по строкам.** Граница уровня — малый круг {P : P·s = t_k} → на экране эллипс
с центром R·t_k·(sx, sy) и полуосями R·√(1−t_k²) (поперёк (sx, sy)) и R·√(1−t_k²)·|sz|
(вдоль). Для строки y — квадратное уравнение: x = xc(y) ± w(y), где xc линейна по y
(прибавление), w² — квадратичная (приращения), √ — «догоняющий» целочисленный корень,
как у диска заглушки (`scr_geo.c:307–308`). Из двух решений берутся лежащие на
видимой стороне: z = (t_k·R − sx·x − sy·y)/sz > 0 — линейная проверка. ~60 тактов на
(строку, уровень), 1.3–2 тыс. пар на кадр. Работает при любом наклоне и с сезонами
(sy ≠ 0). Это и есть «Брезенхем» для тени. Особый случай — солнце у края диска
(|sz| → 0): эллипс вырождается в отрезок, граница уровня — прямая x·sx + y·sy = t_k·R
(отдельная ветка, тоже приращениями).

**Проход 2 (BLT2).** Вдоль строки уровни идут «ложбиной» (k убывает до 0, потом растёт) —
не больше двух участков k > 0. На каждую полосу: источник — блок констант уровня k
(256 байт по `0x0k`), приёмник — продолжение; BLT2 по полубайтам с насыщением добавляет
k ко всем пикселям полосы: суша → ровно `getLandShadow`.

**Океан** получает то же +k, поэтому в проходе 1 отрезки океана заливаются
«с поправкой»: база = цель − k, где цель — `OCEAN + c_k`, а младший полубайт цели ≥ k
(иначе сложение не дойдёт до нужной группы). Уровни k = 0..10 → c_k = 0, 4, 7, 10, 13,
15, 22, 23, 25, 28, 31 (идеал 3k+1; расхождение на уровнях 5–7 — 1–3 шага пологого
градиента, ~1 единица 6-бит). Годится для UFO (192) и TFTD (16): арифметика только по
младшему полубайту. Палитру не трогаем — у TFTD панель GEOBORD сама использует блок
«океана» (250 пикселей, замер `analyze.js`).

**Шум и дизеринг бесплатно.** Блоки прохода 2 могут быть не однородными: «k, k+1»
через байт (шахматка на границе полосы, фаза — по чётности строки) или k/k−1 по
случайной маске (4 строки маски × 10 уровней = 40 блоков в странице) — аналог шума
OpenXcom `G:198` без единого такта процессора.

**Когда пересчитывать.** Угол солнца (время суток × 360°) квантуется «эпохой» ~0.5–1°:
перерисовка тени — при смене эпохи. 5 с — раз в 2–5 с реального времени; 1 мин — раз
в 2–4 такта; 5 мин и больше — каждый такт (5 кадров); «1 день» — 360° за такт, эпоха не
меняется, терминатор стоит (как в OpenXcom).

### 6.5 DMA-композитор

**Раскладка развёрнутых узоров** (набор текущего зума, 8 страниц пула): страница j —
строки узора 4j..4j+3; в странице блоки по 256 байт: 4 строки × 13 текстур (52 блока) +
11 блоков океана (однородные 256 байт цвета «база_k») = **63 блока из 64** (`DMASAddrH` —
6 бит). Блок (r, t) = строка r узора t, повторённая 8 раз. Строится при входе в
геоскейп и смене набора (зумы 1→2, 3→4) из `TEXTURE.DAT`: копия 32 байт + копия «на себя
со сдвигом 32» (DMA читает и пишет по словам по порядку — узор размножается), 2 запуска
на блок, ~832 запуска ≈ 0.5 кадра. Держать все три набора — 24 страницы (переключение
бесплатно) — только если пул позволит (открытый вопрос 4).

**Проход 1, строка y** (r = y & 31, страница `STRIP + r/4`):
```
DMADAddr = задний буфер (280 + y, x_левый)     ; 3 OUT на строку
DMASAddr = (стр., блок первого отрезка, x_левый) ; 3 OUT на строку
для каждого отрезка:                            ; x — неявно (§4 п. 2)
    ld b,#27
w:  in f,(c)        ; 12   DMAStatus, ждать конца прошлого
    jp m,w          ; 10
    ld b,#1C
    outi            ; 16   → #1BAF  DMASAddrH = блок (r&3)·13+t или океан 52+k
    ld b,#27
    outi            ; 16   → #26AF  DMALen = слов − 1
    ld b,#27
    out (c),e       ; 12   → #27AF  DMACtrl = RAM→RAM, старт
    dec d
    jr nz,…         ; ≈110 тактов на отрезок, данные — пара байт из списка строки
```
**Проход 2** — то же с блоками констант (своя страница, 40 блоков) и `DMACtrl` =
BLT2 | OPT (ASZ = 0, без ALGN), приёмник — начало первой полосы k > 0.

**Чётность.** DMA пишет словами → границы отрезков по чётным x. Вариант А (по
умолчанию для зумов 0–1 — проверить глазами): округлять границы к чётным (лесенка
2 пикселя по горизонтали; превью `*_port11_even.png` на глаз не отличить). Вариант Б:
после строки процессор правит пиксель x−1 у каждой нечётной границы (~50 тактов,
1–2 тыс. на кадр зума 0 ≈ +0.3 кадра).

**Короткие отрезки** (< 8 пикселей) можно копировать процессором цепочкой `LDI`
(16 тактов/байт) — на зуме 0 примерно равноценно DMA; решить по профилю.

### 6.6 Буферы и окно

- Задний буфер: строки 280–479, x 0–255 (страницы #18–#1E), не пересекается с полем
  Dogfight (строки 200–275).
- Фон вне диска (зумы 0–1): при смене зума — копия левых 256 столбцов GEOBORD

### 6.11 Режимы качества при вращении

Пока клавиша/кнопка/мышь вращает — «быстрый кадр»: вершины приращениями, без прохода 2
(суша без тени, океан — уровнями по проходу 1 или одним цветом), без оверлеев кроме
меток; после отпускания — полный кадр. Зум 0–1: 14–22 к/с вместо 8–11. Решение —
за пользователем (вопрос 2).

## 9. Поэтапный план

Правило пользователя: сначала C, асм — системное (DMA) и горячее по профилю. Питатель DMA
(внутренние циклы §6.5) — системный, на асм с первого этапа (десятки байт); всё
остальное — сначала C.

**Этап 0. Конвертер и эталоны** (C#). Ресурс `GLOBE` (вершины, многоугольники по ячейкам,
полилинии), `TEXTURE.DAT`, метки; эталонные PNG OpenXcom для 12 видов (6 зумов × 2 вида)
обеих игр. Проверка: `OxzConv dump`, превью. *Готово, когда* превью совпадает с
`tmp/globe_research/png/*_ref.png`.

**Этап 1. Геометрия без тени** (C + асм-питатель DMA, банк 24). Проекция Q14 (сначала
только 16 бит), отсев, заливка М4а, склейка, проход 1, задний буфер, копия; зумы 0–5
(клавиши `+`/`−` и кнопки GEOBORD), вращение 15° → шаги OpenXcom, центр правой
кнопкой, `to_screen`/`from_screen` настоящие, зум в `ST`. Метки пока квадратами
(как сейчас). Тест `tests/globe.oxs`: новая игра → база → геоскейп; для каждого зума —
снимок `tmp/shots/globe/zN_*.png`; вращение 10 шагов; обе игры (сборка `-Game UFO`);
лист — `tools/shotsheet.ps1`; `shotdiff` с эталоном — порог по числу пикселей.
Замер: `profile on … profile off 30` вокруг рендера, строки `ui: screen 32, K frames`.
*Готово, когда* картинка совпадает с эталоном без тени, есть цифры кадров на зумах.
Ожидание на C: 10–20 кадров зум 0, 4–8 зум 5.

**Этап 2. Тень.** Эллипсы уровней, проход 2 (BLT2), уровни океана c_k, эпоха солнца,
кэш геометрии, запасной путь без BLT2 (проверка при старте). Тест: скорость «1 час»,
снимки через N тактов, сравнение с эталоном при том же времени. *Готово, когда*
расхождение с эталоном — только полосы/шум.

**Этап 3. Метки и клики.** Кадры `GlobeMarkers`, мигание 100 мс, восстановление из
заднего буфера, `getTargets` по настоящей проекции (радиус 5 уже есть,
`scr_geo.c:366`). Тест `aliens.oxs` / `dogfight.oxs` (снимки с метками НЛО), клик по
метке → окно.

**Этап 4. Оверлеи.** Границы, подписи, города, радары (клавиша), круги при выборе
места базы, круг дальности в SelectDestination (14_todo §3.3), пути кораблей; клавиши
деталей/радаров. Снимки на зумах 1–3.

**Этап 5. Асм и оптимизация по профилю.** Проекция 8 бит (квадраты) на зумах 0–1,
приращения при вращении, шаг рёбер, сортировка/склейка, эллипсы; режим «быстрый кадр»
(§6.11); М4б — если зум 0–1 медленнее цели. *Цель:* зум 0 полный ≤ 5 кадров, вращение
≤ 3; зум 5 полный ≤ 2.

**Этап 6. Мелочи OpenXcom** (наставление «мелочи обязательны»): наезд перед боем и
отдаление после (14_todo §3.5), сезоны (опция), отладочные рамки зон, перетаскивание
мышью с порогом (`dragScrollPixelTolerance`), `AIRBORNE` для TFTD уже есть.

**Этап 7 (по желанию).** Оверлеи на тайловом слое TSU, метки спрайтами (мигание палитрой).

Оценка кода: банк 24 — C ~12 КБ на этапах 1–2, после асм ~7–8 КБ + таблицы 3–5 КБ;
банк 25 — ~8–10 КБ. Проверка размеров — checkmap сборки (≤ 16 КБ на банк).

## 10. Риски

| Риск | Что делать |
|---|---|
| модель тактов оптимистична (накладные C, промахи кэша Win3) | этап 1 — сразу профиль; режим «быстрый кадр»; М4б; держать вершины в странице банка (кэш) |

   вместо 8–11 на зуме 0) — да / нет / только на зумах 0–1?
3. **Наезд перед воздушным боем**: 10 полных кадров (~0.8 с) или облегчённый (без тени,
   через шаг)?

   `memmap.h`/`build.ps1`) и держать все три набора узоров (24 страницы, смена зума без
   задержки) — или один набор (8 страниц, пересборка ~0.5 кадра при смене зума 1↔2, 3↔4)?
