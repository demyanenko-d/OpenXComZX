# План ускорения отрисовки боя (этап Б1+)

Рабочий план на ближайшие шаги. Основания — замеры 18 сентября 2026: шесть прототипов на
реальных данных обеих игр (`tools/proto/opt1..opt6_*.js`, картинки `tmp/proto/opt*/`) и
микробенчмарк DMA в эмуляторе. Числа и подробности — [16_battlescape_plan.md](16_battlescape_plan.md)
§8.3c–j, здесь — что именно делать, где и как проверять.

## 0. Где мы сейчас

Экран `SCR_BATTLE` (банк 28, `src/battlescape/scr_battle.c`) рисует готовую карту из `BATTLE.PAK`:
уровни снизу вверх, ряды Y, внутри ряда X, внутри клетки — пол, западная стена, северная стена,
объект. Отсева нет. Вход — отладочное меню, первая строка «Battlescape». Тесты: `bat_render.oxs`
(снимки в `tmp/shots/bat/`), `bat_bench.oxs` (микробенчмарк DMA).

Полная перерисовка вида — **24–32 кадра** (0.5–0.64 с). Из них:

| Статья | Кадров | Откуда |
|---|---:|---|
| байты через DMA (186 КБ при 72–74 КБ/кадр) | 2.6 | §8.3f |
| | | |
| *Единицы:* здесь и в 16 §8.3 «такт» — такт шкалы 3.5 МГц, как их считает профилировщик эмулятора (кадр = 71 680). Игра идёт на 14 МГц (`boot.c:103`), то есть в реальных тактах Z80 кадр вчетверо больше — 286 720 (02 §2); доли кадра от этого не меняются. | | |
| настройка 1489 запусков (103 T каждый) | 2.1 | §8.3f |
| **обвязка на C в `blit_tile`/`draw_map`** | **~20** | разность |

То есть узкое место сегодня — не железо, а код на C. Отсюда порядок работ.

## 1. Цели

| Что | Сейчас | Цель |
|---|---:|---:|
| полная перерисовка вида (вход в бой, смена этажа) | 24–32 кадра | ≤ 5 |
| шаг камеры на клетку | 24–32 (полная перерисовка) | ≤ 1 |
| шаг бойца, фаза ходьбы | 24–32 | ≤ 0.5 |
| открытие двери, кадр дыма | 24–32 | ≤ 0.5 |

Инвариант на всех шагах: **картинка совпадает с эталоном попиксельно**. Эталон даёт конвертер
(`tmp/preview/<игра>/BATMAP*.png`, `OxzConv/Core/Battle.cs:RenderPreview`), сверка — снимок
эмулятора против него; плюс попиксельные сверки внутри прототипов (уже сделаны).

## 2. Шаг 1 — блит на ассемблере

**Зачем.** Даёт ×4–5, ни от чего не зависит, ничего не ломает (§8.3f, §9.3).

**Что делать.** Новый `src/battlescape/blit.s` в банке 28 (`tools/build.ps1`, `$banks`, n = 28).
Функция вместо нынешней `blit_tile` (`scr_battle.c:56-102`), соглашение `--sdcccall 1`.
Вход: номер кадра, `x`, `y`. Таблица кадров уже лежит в памяти банка (`tile_tab`, `__at(0xB800)`),
база данных кадров — `tile_data`.

Что должен делать блит (всё это есть в нынешнем C, переносится один в один):
- взять запись кадра (6 байт: `x, y, w, h, смещение/2`), сложить с позицией клетки;
- срез строк сверху (кадр выше окна) и снизу (ниже строки 143) — сдвигом смещения и высоты;
- обрезка по X: при полной ширине — один запуск на полосу (`DMANUM = n-1`), при обрезанной —
  запуск на строку (источник перестаёт быть линейным);
- разрыв полосы на границе страницы экрана (32 строки);
- нечётный `x` — запасной путь (сейчас `gfx_sprite`; после шага 3 такого случая не останется).

**Цель по тактам.** ≤ 600 T на часть клетки против нынешних ~3000 (полезной работы — настройка
восьми регистров, 103 T по замеру).

**Проверка.** `bat_render.oxs` — снимки не изменились (сверить с `tmp/shots/bat/` до правки);
профиль в том же тесте: доля `blit_tile` должна упасть с 44 % до единиц процентов; полная
перерисовка — ожидаемо 6–9 кадров.

**Риск.** Соглашение о вызовах SDCC 4.5 (`--sdcccall 1`) и передача пятерых параметров — сверить
с уже написанным ассемблером проекта (`src/geoscape/earth/globe_s.s`, `globe_sh_s.s`).

## 3. Шаг 2 — кольцевой буфер и аппаратный скролл

**Зачем.** Убирает полную перерисовку из типового цикла: шаг камеры 0.6–1.7 кадра, шаг бойца
0.09–0.43 (§8.3h).

**Что делать.**
1. Карта живёт в кольцевом буфере видеопамяти 512×512: мировой пиксель → буфер это `mod 512` по
   обеим осям, камера — `GXOffs = camX mod 512`, `GYOffs = camY mod 512`. Заворот 9-битных
   регистров совпадает с кольцом, поэтому **перебазирования по X не нужно никогда**.
2. Панель ICONS — сплит-экраном. Начать с **раскладки А**: панель в строках 456..511 того же
   холста, карте остаются 0..455, `GYOffs ∈ [0, 312]`, перебазирование раз в ~39 вертикальных
   шагов (копия 2D-DMA 512×312 ≈ 156 КБ или просто полная перерисовка). Раскладка Б (на строке 143
   переписывать `GYOffs` **и** `VPage`, панель в своих двух страницах, перебазирований ноль) —
   после проверки в эмуляторе, что смена `VPage` посреди кадра работает.
3. «Область годности» — мировой прямоугольник, выровненный наружу по решётке 16 по X и 8 по Y.
   При движении камеры дорисовывается только въехавшая полоса.
4. `repaint(rect)`: перерисовка прямоугольника с **обрезкой блитов по нему** (без обрезки —
   925–1274 неверных точки, §8.3h) и перебором клеток по правилу зависимостей:
   `|a − b| ≤ 1` и `|(a+b) − 3c| ≤ 6` для местности, `|a − b| ≤ 3` и `|(a+b) − 3c| ≤ 9` с юнитами
   (максимум `P_Level`: TFTD 19, UFO 16 — берём запас в один уровень).
5. Объединение грязных прямоугольников: объединять, когда площадь объединения ≤ ~2× суммы
   площадей (это примерно с 16 разбросанных клеток). Анимацию дыма объединять всегда — 25
   отдельных прямоугольников дороже полной перерисовки.

**Проверка.** Новый `tests/bat_scroll.oxs`: проехать камерой по маршруту, на каждом шаге снимок;
отдельно — снимок после маршрута против снимка «полная перерисовка той же позиции» (должны
совпасть побайтно, `tools/shotdiff.ps1`). Профиль: шаг камеры ≤ 1 кадр.

**Риск.** Блит, пересекающий заворот 512, режется на два; смена `VPage` посреди кадра (раскладка Б)
требует проверки на эмуляторе, а потом на железе.

## 4. Шаг 3 — тайлсет половинками по 16 пикселей

**Зачем.** Обрезка по X рвёт линейность источника и даёт запуск DMA на каждую строку: на шаге
камеры в городе это 1459 запусков (1.5 кадра только на настройку) против 94 с половинками (§8.3h).
Заодно исчезает случай «нечётный x» в блите.

**Что делать.** `OxzConv/Core/Battle.cs`: класть кадр тайла двумя записями SPRSET — левая и правая
половины по 16 пикселей (границы обрезки всегда кратны 16 относительно клетки). Точек столько же,
плата ~3 КБ на вторые записи. В движке блит выбирает нужные половины.

**Проверка.** Конвертер прогоняется на обеих играх; снимки `bat_render.oxs` не изменились; в
профиле число запусков DMA на шаг камеры падает примерно в 15 раз.

## 5. Шаг 4 — усечение строк по перекрытию

**Зачем.** −52 % байт и −40 % блитов, на плотных картах до −83 %; **память в тайлсете не нужна** —
срез строк это тот же кадр с другим смещением и высотой (§8.3g).

**Что делать.**
1. Пока карты прегенерированы, усечение считает **конвертер** (перекрытие — свойство карты, от
   камеры не зависит): проход по клеткам от ближних к дальним с битовой картой экрана,
   результат — по байту на часть клетки (сколько строк сверху и снизу можно не переносить).
2. Формат `BATMAP` (09 §6) дополняется массивом усечений: 4 байта на клетку, после массива клеток.
3. Движок передаёт `top`/`bot` в блит — механизм среза там уже есть.
4. Когда появится генератор карт, тот же проход делается при загрузке (накопитель 320×144 бит =
   5.7 КБ, кэш усечений 4 страницы на карту 60×60×4).

**Тонкости.** Анимация и двери НЛО: у закрывающего берётся пересечение кадров `Frame[0..7]`, у
закрываемого — объединение (цена — доли процента). Неразведанные клетки при тумане войны нельзя
«не рисовать вовсе» — заливать чёрным по габаритам их спрайтов, иначе усечение за ними неверно.

**Проверка.** Снимок против эталона конвертера — побайтно; на TFTD XBASES ожидаем падение числа
блитов примерно в 6 раз.

## 6. Шаг 5 — склейка клеток и подложка местности

**Зачем.** ×3–11 на полной перерисовке, 1 блит вместо 13–17 на шаге бойца (§8.3d).

**Что делать.**
1. **Склейка клетки**: ключ — четвёрка номеров тайлов; на карте 50×50 уникальных сочетаний
   66–339, в одном виде 26–94, то есть 79–96 % клеток вида берутся из кеша. Кеш — 3–21 страница
   пула, предсборка при загрузке карты (20–100 мс).
2. **Подложка**: уровни ниже текущего сведены в один буфер и переносятся непрозрачным RAM→RAM
   (45 КБ одной копией). Держать её в буфере прокрутки, чтобы сдвиг камеры не требовал пересборки.
3. Клетки с анимированными частями мимо кеша (0–8 % на большинстве террейнов, но UFO UBASE 29 % и
   TFTD GRUNGE 63 % — там либо 8 фаз в кеше, либо по частям).
4. Разрушение даёт новую сигнатуру: в 9–93 % случаев (медиана ~36 %) она уже в кеше, иначе ~4 тыс. T
   на сборку.

Полы отдельным приёмом не делаем — они частный случай подложки (§8.3i); от той темы берём вывод
«плоскость пола заведомо непрозрачна, копировать её законно» и, если понадобится, резку спрайта
пола на «ромб» и «остаток» в конвертере.

**Проверка.** Снимки против эталона; профиль: полная перерисовка на TFTD XBASES-подобной карте
должна упасть в разы.

## 7. Шаг 6 — буфер «чистой карты»

**Зачем.** Стирание юнитов, дыма и курсора копией вместо перерисовки: фаза ходьбы дешевеет в 4–5
раз, кадр дыма — в 3.4–5.8 (§8.3h). Делать, когда появятся юниты и эффекты.

**Что делать.** Второй буфер 512×512 (16 страниц из ~160 доступных бою) хранит местность без
динамики; стирание — RAM→RAM из него.

## 8. Порядок и зависимости

```
шаг 1 (asm-блит) ─┬─> шаг 2 (кольцевой буфер, скролл) ─> шаг 6 (чистая карта)
                  ├─> шаг 3 (половинки) ──> усиливает шаг 2
                  ├─> шаг 4 (усечение строк)
                  └─> шаг 5 (склейка, подложка)
```

Шаги 3–5 независимы друг от друга и перемножаются. Шаг 2 — самый заметный для игрока (плавный
скролл), но без шага 1 упрётся в ту же обвязку на C.

## 9. Чего не делаем (замерено, отрицательно)

- спан-буфер по строкам экрана и любой отсев мельче 2–3 строк спрайта: запуск DMA стоит как
  перенос ~105 байт, средний спан — 14 байт (§8.3e, §8.3f);
- склейка «колонкой» по экранной диагонали — неточна, 2.2–15.9 тыс. неверных точек (§8.3d);
- метатайлы 2×2/3×3 как кеш — 18–179 страниц (§8.3d);
- усечённые варианты кадров в тайлсете и срез по столбцам — не нужны и не окупаются (§8.3g);
- туман войны как способ рисовать меньше — при камере на бойце экономия 0–3 % (§8.3c);
- упрощённый вид при скролле и прогрессивная отрисовка (§8.3c);
- `FILL` для полов — они текстурированные (§8.3i);
- разметка комнат flood fill для рендера — неточна; оставить для логики (§8.3e).

## 10. Критерии готовности этапа

1. `tests/bat_render.oxs` и новый `tests/bat_scroll.oxs` проходят, снимки совпадают с эталоном
   конвертера побайтно.
2. Профиль в эмуляторе: полная перерисовка ≤ 5 кадров, шаг камеры ≤ 1, шаг бойца ≤ 0.5.
3. `runtests.ps1` зелёный целиком.
4. Числа занесены в 16 §8.3b (таблица замеров) и сюда, в §0.
