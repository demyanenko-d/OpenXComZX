# 23. Дистрибутив: карта для реального железа

Сборка «всё, что нужно для игры на настоящем ZX Evolution» одной командой:

```
powershell -File tools\dist.ps1            # собрать обе игры и карту
powershell -File tools\dist.ps1 -NoBuild   # только разложить и собрать образ
```

- `distr\` в корне проекта — **содержимое карты** (что копируется в её корень);
- `oxz_card.img` в корне проекта — **образ этой же карты**: и для эмулятора
  (`run.ps1` → `ZC.SDCARD`), и для записи на карту целиком.

Это единственные артефакты вне `tmp\` (просьба пользователя: дистрибутив под
рукой). В git не попадают — `.gitignore`, данные игр распространению не
подлежат. Скрипт — `tools/dist.ps1`, текст инструкции для пользователя —
`tools/dist_readme.txt` (на карте — `README.TXT`, UTF-8).

## 1. Что делает скрипт

1. Собирает обе игры: `build.ps1 -Game UFO -NoCard`, затем `-Game TFTD -NoCard`
   (TFTD последней, чтобы рабочее дерево осталось на игре по умолчанию; `-NoCard`
   — чтобы образ собирался один раз в конце, а не на каждую игру). Код возврата
   `build.ps1` проверяется: при ошибке компиляции скрипт падает (иначе ловушка —
   старый `oxz.spg` от прошлой сборки, см. `findings_log`).
2. Раскладывает `distr\` — это ровно содержимое корня карты:

   | На карте | Откуда | Размер |
   |---|---|---|
   | `OXZTFTD.SPG` | сборка TFTD | 1 092 КБ |
   | `OXZUFO.SPG` | сборка UFO | 958 КБ |
   | `OXZ/TFTD/*.PAK` | `tmp/sd/OXZ/TFTD` (конвертер) | 32 МБ |
   | `OXZ/UFO/*.PAK` | `tmp/sd/OXZ/UFO` | 22 МБ |
   | `boot.$C`, `WC/`, `Help.txt` | `unreal/soft/WC/exe` | 470 КБ |
   | `README.TXT` | `tools/dist_readme.txt` | 4 КБ |

   Из состава Wild Commander взяты только загрузчик, папка `WC` и справка:
   `demo/` (44 МБ чужих демок) и `soft/` (текстовый процессор в `.SCL`) карте
   не нужны. Пакетов на игру — 13, список в скрипте (`$packs`) повторяет
   `pack_name` в `sdres.c` плюс музыку (`music.c`) и глобус (`globe_view.s`);
   новый пакет в конвертере — добавить и сюда, иначе он не попадёт на карту.
   Папка `OXZ\<игра>` перед копированием чистится: устаревших пакетов на карте
   быть не должно.
3. Делает из `distr\` образ `oxz_card.img` утилитой
   `unreal/tools/robimg/robimg.exe`. Образ — вне `distr\`: иначе robimg
   копирует его внутрь самого себя.

`build.ps1` свой образ больше не собирает: если карты нет или данные конвертера
новее образа, он зовёт `dist.ps1 -NoBuild` (игры не пересобираются, SPG берутся
те, что уже лежат в `distr\`). Так тесты всегда идут с той же карты, что уедет
на железо.

## 2. Карта обязана быть FAT32

TS-BIOS грузится **только с FAT32**: на FAT16 он пишет

```
System Meditation:
FAT32 NOT FOUND!
Press SS + Reset to change start-up options
```

(проверено пользователем на образе 128 МБ / FAT16 — первый вариант этого
скрипта). Сам порт читает и FAT16, и FAT32 (`fat.c`), но до порта дело не
доходит — загрузчик читает TS-BIOS.

`robimg` тип FAT не спрашивает, а выбирает по числу кластеров (FAT16, пока их
≤ 65525), поэтому FAT32 получается только на достаточном объёме:

| `-s` (КБ) | `-o` (кластер) | Итог |
|---|---|---|
| 131072 (128 МБ) | 4096 | FAT16 |
| 131072 | 1024 | FAT32 |
| 262144 (256 МБ) | 2048 | **FAT32 — берём это** |
| 262144 | 4096 | `Format ... Error e`, код возврата 0, в образе один MBR без BPB |
| 524288 (512 МБ) | 4096 | FAT32 |

Команды:

```
robimg.exe -p=<образ> -s=262144 -o=2048 -f=0     # создать и отформатировать
robimg.exe -p=<образ> -a=1 -C=<папка>            # залить содержимое папки
```

- `-s` — размер в КБ, `-o` — размер кластера в байтах, `-f` — тип разметки
  (`0` — раздел в MBR, `1` — том с сектора 0 без MBR; **по умолчанию 1**),
  `-a=1` — не форматировать уже готовый образ.
- Берём `-f=0`: карта, отформатированная из Windows, тоже с разделом в MBR, и
  образ для эмулятора должен повторять её. `fat.c` читает оба варианта
  (сектор 0: `EB`/`E9` — сразу BPB, иначе первый FAT-раздел MBR).
- Длинных имён robimg не умеет — в образе они усечены до 8.3
  (`WC/MENU/HRUSTV~1.SPG`). На игру это не влияет (все наши имена 8.3),
  но родное меню WC (`wc.mnu` ссылается на длинные имена) в образе не работает;
  на настоящей карте, скопированной из Windows, имена сохранятся.

Содержимое готового образа можно посмотреть без эмулятора:

```
node tools\fatls.js oxz_card.img
```

## 3. Проверка

- `tools/runtests.ps1` на этом образе — 21 сценарий зелёный (FAT32 + MBR: в
  `fat.c` это другая ветка разбора тома и другая `fat_next`/`chain_skip`, чем
  на прежнем FAT16 без MBR).
- На подменённой сборке UFO — `ufopaedia_ufo`, `globe`, `bat_render`: обе игры
  находят свои пакеты (`sd: OXZ/UFO/BACK.PAK 17` …), бой генерирует карту.
- `tests/boot_card.oxs` (`run.ps1 -Boot -Script tests\boot_card.oxs -Headless`) —
  старт без снапшота, как на железе: снимки в `tmp/shots/boot/`.
  **Ограничение эмулятора**: TS-BIOS в Unreal всегда уходит в Setup (CMOS нигде
  не сохраняется), а выход из Setup — F12, которого машине не передать: Unreal
  забирает F12 себе под сброс, PS/2-буфер (`input.buffer`, включается гостевой
  записью 2 в CMOS ≥ `#F0`) в Setup выключен, а в матрицу ZX F-клавиши не
  входят. Команда сценария `pckey <имя|hex>` шлёт скан-код PS/2 в буфер и
  печатает его состояние — для кода, который буфер включает. Поэтому цепочка
  «TS-BIOS → boot.$C → Wild Commander → ENTER на SPG» проверяется только на
  живой машине или в эмуляторе руками.

## 4. Как этим пользоваться на железе

Кратко (подробно и по-человечески — в `README.TXT` на карте):

1. Карта SD/microSD от 128 МБ, один раздел **FAT32**, содержимое `distr\` —
   в корень карты.
2. Пути к данным зашиты как `OXZ/<игра>/<пакет>.PAK` **от корня карты**:
   папку `OXZ` переносить и переименовывать нельзя.
3. Карта в разъём SD (zc), в TS-BIOS (Shift+F12) выбрать её загрузочным
   устройством — загрузится Wild Commander, `ENTER` на `OXZTFTD.SPG`
   (или `OXZUFO.SPG`) запускает игру. `wc.ini` уже ставит 14 МГц
   (`CPU_FREQ=2`).
4. Сохранения пишутся на карту (`fat_write` по месту) — защита записи
   должна быть снята.

Данные `*.PAK` сконвертированы из оригинальных игр и распространению не
подлежат (`06_original_data.md`): в репозитории их нет, каждый собирает
карту из своей копии.

## 5. Диагностика SD на чужой машине

Первый запуск на стороннем эмуляторе TS-Config (2026-10-23): игра дошла до глобуса, но
**без заставки, без фонов окон и без музыки**, хотя на карте лежал весь `distr/`. Это ровно
граница «вшито в SPG / с карты»: `RULES`, `LANG`, `PAL`, `GEO`, `MCD` — в SPG (меню,
тексты, глобус работают), `CUTS`, `BACK`, `MUSIC*` — с карты. Отладочный вывод игры
(`#F8AF`, 07 §4) виден только нашему Unreal, поэтому причину пришлось бы гадать.

**Окно диагностики** (`SCR_SDINFO = 14`, `src/kernel/sddiag.c` в банке 14, раскладка — в
`scr_menu.c`): главное меню раз за запуск зовёт `sddiag_run(0)` и открывает окно само,
если пакеты не открылись (`sd_state == 2`) или чтение не работает и посекторно
(расхождение пачки с посекторным при включённом запасном пути — не беда, см. ниже).
Вручную — кнопка DEBUG главного меню, последняя строка «SD card diagnostics». Окно без
фоновой картинки (фон тоже с карты), всё на одном экране — тестировщику хватает фото.

| Строка | Что показывает | Откуда |
|---|---|---|
| Card | тип карты (SDHC/SDXC — блочная адресация, SDSC — байтовая) или «NOT READY at <шаг>, R1=xx» | `sd.s`: `_sd_type`, `_sd_step` (1 CMD0, 2 CMD8, 3 ACMD41, 4 CMD58, 5 CMD16), `_sd_r1` |
| Volume | FAT16/FAT32, тип раздела MBR и LBA тома, либо «MOUNT ERROR: …» | `fat_mount`, `fat_info` |
| Cluster | размер кластера, первый сектор данных | `fat_info` |
| Read test | 2 сектора `BACK.PAK` пачкой (`CMD18` + DMA SPI→RAM) и посекторно (`CMD17` + `INIR`), сравнение | `fat_read` с чётным / нечётным приёмником |
| CMD18+DMA / CMD17 | первые 8 байт обоих чтений (или с места расхождения) | там же |
| 13 строк пакетов | «OK N res, K KB, R runs» / NOT FOUND / FRAGMENTED / BAD HEADER / OTHER GAME | `fat_open` + первые 8 байт (`OXZP`, у `GVIEW` — `GVE2`; байт игры) |

Почему именно «пачка против посекторного»: том, каталоги и заголовки пакетов читаются
`sd_rd` (`CMD17`, байты через `INIR`), а ресурсы — `sd_rdm` (`CMD18`, каждый блок —
DMA SPI→RAM, `sd.s`). Эмулятор без канала DMA SPI (или без `CMD18`) даёт ровно
наблюдаемую картину: пакеты находятся, внутри — пусто. Страница-приёмник заранее залита
узором (`#55` под пачку, `#AA` под посекторное), поэтому «DMA ничего не записал» видно
сразу: строка `CMD18+DMA` — `55 55 55 …`.

**Проверено в нашем Unreal** (сценарии, все в `runtests.ps1`; снимки —
`tmp/shots/sdinfo/`):

| Сценарий | Условие | Итог в окне |
|---|---|---|
| `sdinfo.oxs` | норма (SDSC) | всё OK, окно само не открывается |
| `sdinfo_dma.oxs` | `fault dmaspi 1` — DMA SPI→RAM не пишет в память | само не открывается (игра цела, читает посекторно); на главном меню — «TS-Config: SD without DMA» и настоящий фон; открытое запросом — MISMATCH at byte 0, using CMD17, `55 55 …` против `4F 58 5A 50 …`, пакеты OK |
| `sdinfo_sdhc.oxs` | `ZC.SDHC=1` — карта с блочной адресацией | SDHC/SDXC, всё OK |
| `sdinfo_nocard.oxs` | `ZC.SDCARD=` — карты нет | открывается само: NOT READY at CMD0, R1=FF; MOUNT ERROR: NO CARD |

Попутно выяснилось: **Unreal эмулировал только SDSC** (OCR без бита CCS, `fseek` по
аргументу команды как по байтам), и ветка `CT_BLOCK` драйвера (`sd.s` `set_arg`) не
выполнялась ни разу, хотя любая карта от 4 ГБ — SDHC/SDXC. Добавлен режим `ZC.SDHC=1`
(`unreal/…/sdcard.cpp`, `config.cpp`): OCR `#C0…`, адрес в блоках по 512 байт.
Под ним зелёные и тяжёлые сценарии (`ufopaedia`, `bat_render`, `campaign`) — ветка SDHC
рабочая, подозреваемый №1 на стороннем эмуляторе — DMA SPI или `CMD18`.

### Запасное чтение без DMA

`fat_mount` после монтирования проверяет пачку сам (`fat.c` `dma_check`): два первых
сектора тома читаются `CMD18` + DMA в страницу пула (залитую `#55`) и посекторно
`CMD17` в `secbuf`; при расхождении или ошибке пачки — `fat_nodma = 1`, и `fat_read`
дальше всё читает посекторно (`CMD17` + `INIR` в `secbuf`, затем `LDIR` в дальнюю память,
`far_write`). Проверка — в `fat_mount`, потому что том монтируют трое независимо (`sdres`,
музыка, глобус), и до чтения любого каталога (каталог `MAPS.PAK` — 4.5 КБ, сам идёт
пачкой). Нет свободной страницы (бой) — проверка пропускается, прежний вывод остаётся.
Ожидание конца DMA в `sd.s` (`dma_sec`) ограничено 65536 опросами (~40 кадров): на машине,
где DMA не кончается, раньше было бы вечное зависание, теперь — отказ пачки и `CMD17`.

Игра на такой машине работает целиком, только медленнее. Окно диагностики при этом само
не всплывает (на каждом запуске оно бы мешало) — вторая строка заголовка главного меню
вместо «ZX Evolution / TS-Config» говорит «TS-Config: SD without DMA».

Проверка: любой сценарий — с `run.ps1 -Set 'ZC.FaultDmaSpi=1'` (в `runtests.ps1` — имя
`сценарий+nodma`, в набор входят `ufopaedia+nodma` и `bat_render+nodma`). Снимки с DMA
и без **совпадают байт в байт** (31 снимок Уфопедии, 5 снимков карт боя). Цена:

| Сценарий | С DMA, кадров | Без DMA | |
|---|---|---|---|
| `ufopaedia` | 1191 | 1675 | +41 % (картинки статей) |
| `bat_render` | 1192 | 1462 | сборка карты боя ~140 → 364 кадра |
| `campaign` | 2722 | 2860 | +5 % |
| `globe` | 485 | 503 | +4 % |
| `inventory` | 362 | 423 | +17 % |

`bat_render.oxs` ждал после сборки карты фиксированные 200 кадров — без DMA нажатия
приходили посреди загрузки и сдвигали камеру; теперь ждёт по метке экрана.

### Флешка с MBR от GRUB (настоящий ZX Evolution, 2026-10-24)

На живой машине: WC с флешки грузится, игра запускается, но без заставки, фонов и музыки —
«ругается на файловую систему». Причина в нашем `fat_mount` (нашла и параллельная сессия,
разбирая журнал загрузки с той же флешки): сектор 0 считался загрузочным сектором тома,
если начинается с перехода `EB`/`E9`. Флешка раньше была установочной Ubuntu (метка
`UBUNTU-SERV`), её MBR — код GRUB, начинается с `EB 63 90`, раздел — с сектора 2048;
быстрое форматирование Windows код MBR не трогает. Игра принимала MBR за том, по смещению
11 читала «размер сектора» `00 00` и возвращала `FAT_NOFS`. TS-BIOS ищет том иначе
(`REF/tsbios/src/pff/pff.c` `check_fs`/`pf_mount`): по подписи `FA` в поле типа ФС, а в
MBR берёт первую запись **без проверки типа раздела**.

Теперь (`fat.c` `is_vbr`): сектор — том, если в нём `55AA` и правдоподобный BPB (512 байт
на сектор, кластер — степень двойки, 1–2 FAT, резерв не ноль); иначе это MBR, и том
ищется в первой из четырёх записей, где по LBA лежит такой сектор. Тип раздела не
проверяется, как у TS-BIOS: Windows при форматировании раздела тип не меняет, и карта
из-под exFAT (`07`) после форматирования в FAT32 остаётся с `07` — прежняя проверка
`04/06/0B/0C/0E` отвергла бы и её.

При ошибке монтирования окно диагностики показывает строку **MBR** (тип и LBA последней
проверенной записи) и сырые байты **sector 0** / **partition** — что за карта, видно по фото.

Сценарии (образы — `tools/cardvariants.js` из `oxz_card.img`, `runtests` зовёт сам):
`sdinfo_grub.oxs` — MBR `EB 63 90`, тип `07`: монтируется, всё OK (старый код — `FAT_NOFS`
по построению: первый байт `EB`, смещение 11 — `00 00`); `sdinfo_nofat.oxs` — запись
раздела указывает на сектор 1: MOUNT ERROR, окно открывается само, байты на месте.

Обход для старых сборок (стирает флешку): `diskpart` → `list disk` → `select disk N`
(N — именно флешка, сверить по размеру) → `clean` → `create partition primary` →
`format fs=fat32 quick` → `active`; код MBR тогда начинается с `33 C0`.
